# Library player

The player uses Navidrome as the playback server. Musimo keeps its local SQLite index for download ownership, while Navidrome supplies playable IDs, library browsing, audio streams, cover art, lyrics, scrobbles and the saved play queue.

## Configuration

Set `navidrome_url` to the address reachable from the Musimo container. Mount a JSON credentials file containing `username` and `password`, then set `MUSIMO_NAVIDROME_CREDENTIALS_FILE` to its container path. The same file supports selective scanning and playback. Credentials remain on the backend. Browser requests use same-origin Musimo endpoints and never receive the password or salted Subsonic token.

`navidrome_url` accepts HTTP or HTTPS, including a path prefix. Credentials, query strings, fragments and non-HTTP schemes are rejected. The capability endpoint reports an unavailable state instead of failing when Navidrome is not configured or cannot be reached.

## Player experience

Library has Home, Albums, Artists, Tracks and Playlists views. Each view and detail page has its own URL, so refresh and browser Back preserve page navigation. Albums opened from an artist use `/library/artists/{artist}/albums/{album}` and return to that artist. An artist's All songs view uses `/library/artists/{id}/songs`. One search field searches the active view; album, artist and track searches run against Navidrome, while the smaller playlist list is filtered in the browser. Sort choices are specific to each view. More results load as you scroll. Grid and list layouts are available for collection views and the choice is remembered in the browser. Artist images come from Navidrome. Artist, album and playlist rows can open, play or shuffle their collection. On album cards, the artwork play button starts the album while the remaining card opens its songs. Album cards and rows carry the release year. Opening an album or playlist reveals its tracks, and Play all and Shuffle both create one persistent queue. The footer player provides seek, previous, next, shuffle, repeat, volume and mute. Its artist and album names open their Library pages, and both its expand button and the cover thumbnail open Now Playing. While a library track plays, the cover wears a slow accent ring as a hint that there is more behind it; the ring goes away when paused and holds still under `prefers-reduced-motion`. A catalog preview's cover is only a picture. While playing a library track, a thumbs up button toggles membership in the default linked playlist, and a plus button opens a playlist picker. The queue and position restore from Navidrome after a refresh. Browser media controls receive the current title, artist, album and artwork.

On a phone (under 768px wide) the footer is a mini player: one row with the artwork, title, play or pause, next and close, and a slim seek bar along its top edge. It is hidden until something plays, and again while Now Playing shows a library track, since the page there repeats its title, play or pause, next, close and seek bar. Previous, shuffle, repeat, like and mute are on the Now Playing page, which the artwork or the title opens, and Now Playing offers Add to playlist in place of the footer's plus button. Volume is left to the device's own buttons. A catalog preview gets the same row with play or pause and close.

Any play button becomes a pause button while the thing it starts is the thing playing. For a track that means the track itself; for an album, artist, playlist or the Tracks list it means that collection still owns the queue. Pressing pause again resumes playback rather than refetching.

Albums (and Home), Artists and Tracks run search, genre and year filters, sort order and the match count on the server, so they describe the whole library rather than the pages this browser has scrolled through. On Tracks, Play all and Shuffle do too: Shuffle takes a server-side random sample, and Musimo caps one saved queue at 500 songs, so Play all plays the first 500 songs in the current sort order and Shuffle plays a random 500. Playlist sorts and the playlist visibility filter still work on the loaded list.

An artist page sorts its albums by release date, title or play count, and its All songs view sorts by album order, title, play count, length or release date. The All songs URL (`/library/artists/{id}/songs`) survives refresh and returns the app shell. A popularity chart plots Navidrome's play counts for the artist's dated releases, oldest to newest; it says so plainly when there are not yet enough recorded plays to draw a line.

The liked playlist is the one playlist Musimo maintains, so it is always listed, sorts to the top of every playlist view, and has no delete control. Rename is available for all playlists including the liked playlist; only the delete control is refused for it. `DELETE /api/library/playlists/{id}` refuses it as well, because the thumbs up button depends on it existing. Its identity is the stored link, so the protection begins when Musimo adopts or creates the playlist rather than applying to anything a user happens to name Liked. Other playlists can be created, renamed, emptied and deleted; the delete control appears on hover or focus. Playlist rows show their song count and length and can be filtered by public or private. The playlist picker is a centred modal with a 25 row limit and filter box, opened from the footer player's plus button or from Now Playing's Add to playlist button. The dialog is rendered beside the footer, not inside it, so it still opens while the footer is hidden. The liked playlist is excluded from the picker. Inline New playlist is available with the current song. Each row shows whether the current song is already in that playlist and toggles between Add and Remove, so the same song cannot be added twice, and each row expands into a scrolling list of that playlist's songs where any of them can be removed. The playlist page also offers an Add songs search box. Playlist reads share one cache with the playlist page, so a change made in the player appears there without a reload.

Now Playing is also in the desktop sidebar, as the last row after Diagnostics, with the current cover as a small thumbnail in place of an icon. It exists only while a library track is loaded, and it is last so its arrival or departure moves no other row. The phone bottom bar keeps its five items, which fill its 64px, so a phone reaches Now Playing from the mini player's cover or title.

Now Playing shows the artwork in a stage that can go full screen in the tab or pop out into a floating window (right-clicking it offers Go to album, Go to artist, Add to playlist and Full screen), over a soft wash taken from the cover's dominant colour and mixed into the theme's canvas so text keeps at least AA contrast; the artwork and the wash cross-fade over about 300 ms when the track changes, and cut under `prefers-reduced-motion` (see [the popout note](now-playing-popout.md#backdrop-and-track-changes)). Under the stage are the track's title and every control the footer has, and one panel of tabs, Up next, Lyrics, About and History, beside it (beneath on a phone). Under the artist line the page also sums the file up in one line ("FLAC, 44.1 kHz, 1,012 kbps"); see [About this track](#about-this-track). The seek bar between the two times draws the track's waveform, and the footer player keeps its plain bar; see [Waveform seek bar](#waveform-seek-bar). Up next lists what follows the playing track and, where the player knows the source of the queue, says "Playing from" its name. It is also where the queue is edited; see [Editing the queue](#editing-the-queue). The footer player is hidden while the page shows a library track, on a desktop and a phone, because the page has all of its controls, its close button included; the page repeats the footer's status line only for errors and confirmations, not for "Your Navidrome library" or "Queue restored". The footer publishes `--player-height` as `0px` for as long as it is hidden, so the queue dock and every other offset that adds it up sit where they would with no player; the height comes back when the footer does. See [the popout note](now-playing-popout.md). Musimo asks Navidrome first, then checks LRCLIB when the library track has no imported lyrics. Catalog previews and library tracks have separate audio elements (the library has a pair, see [Gapless playback](#gapless-playback)), and only one of them plays at a time. The library element that is playing also feeds one Web Audio `AudioContext` and `AnalyserNode` for the Now Playing visualizer, whose scene, a fluid simulation, is drawn through a post stack of feedback trails, bloom, beat-driven chromatic aberration, a tonemap and grain; see [the visualizer note](visualizer.md) for why previews must never touch it.

## Editing the queue

The queue can be changed while it plays. The player context offers `playNext(tracks)`, `addToQueue(tracks)`, `removeFromQueue(index)`, `moveInQueue(from, to)` and `clearQueue()`, and every one saves through `PUT /api/player/queue`, the same call the autosave uses. A save that fails says so in the player's status line, since the queue on screen would then differ from the one that restores after a refresh.

Where the actions are:

- **Song rows** on the Tracks list, album pages, playlist pages and an artist's All songs view have a "More actions" menu with Play next and Add to queue.
- **Albums and playlists** have the same menu for the whole collection: on the album and playlist page headers, on list rows, on playlist cards, and on album cards (over the artwork, shown on hover or focus). A card has not loaded its songs, so the menu reads them first.
- **Up next** has, on each row, a drag handle, move up and move down buttons, and a remove button. The playing track is not in Up next and cannot be removed there; skip it instead. Its header has Clear queue, which keeps the playing track, and Save as playlist, which asks for a name and creates a playlist of the whole queue through `POST /api/library/playlists` in one call.

Play next puts songs straight after the playing track, but behind any songs already queued that way, so two Play nexts play in the order they were chosen. Add to queue puts them at the end. With nothing loaded, either one starts playing the songs instead.

Reordering has three routes to the same move. Drag a row by its handle (native pointer events, so touch works, and dragging near the panel's edge scrolls it; Esc cancels). Or use the move buttons. Or press Alt with Up or Down on a row's title button. The result is announced in a polite live region ("Moved Delta to position 2 of 3."), and so are removal, clearing and saving as a playlist. Focus follows the row that moved, and moves to a neighbour when a row is removed.

Shuffle picks the next song at random, so there is no fixed order to edit. Songs you queue by hand are the exception: with shuffle on, the nearest of them after the playing song plays next, in the order Up next shows them, and chance takes over once they are used up. Removing, moving and clearing all act on the queue as it is shown.

Songs queued by hand survive a reload. Navidrome's saved queue holds ids only, so the player keeps their positions in `localStorage` under `musimo.queue-chosen`, beside a hash of the queue's ids in order (`queueHash`). It writes them whenever the queue or the set changes, including when one of them starts playing and stops being "chosen". On restore the positions are read back only if the restored queue hashes the same; a queue that differs (another device changed it, or a save failed) drops them rather than putting the wrong songs first. Browser storage is optional: every read and write is wrapped, and without it a reload simply forgets which songs were chosen.

An edit does not take the collection away. The player keeps the source it began with (`album:…`, `playlist:…` and so on) and tracks separately, as `edited`, that the queue has been changed by hand. Up next says "Playing from album Clear Water, edited", and that collection's play button keeps showing Pause while its own song is the one playing. The source follows the playing track (`queueSource`): while it is a song you added with Play next or Add to queue, the queue counts as `queue` ("Playing from your queue") and the collection's button offers Play again; when a song of the collection plays, it is the collection again. A song row on the collection's page is not marked as the playing one once the queue has been edited, because the queue's places no longer line up with the list.

Three cases use a source of their own instead. Clear queue leaves one song and no collection, so the source becomes `queue`. Play next or Add to queue with nothing loaded starts a queue from those songs, also `queue`. A History row starts its queue with the source `history`. A queue restored after a reload has no known collection (`restored`, so no "Playing from" line), and the first edit to it makes it `queue`.

Navidrome saves at most 500 songs. An addition that would take the queue past that is refused whole, with a message in the player's status line ("The queue is full. Navidrome saves 500 songs and this would make 502. Nothing was added."), and nothing is saved. `PUT /api/player/queue` refuses more than 500 ids as well, so the limit holds even for a client that skips the check. Save as playlist uses the queue's own size, which is within the 500 songs a playlist create accepts.

Starting playback keeps the collection in place. Loading feedback appears in the Library header, and other cards keep their play buttons hidden until hovered or focused. Touch layouts keep the buttons visible.

## Gapless playback

The library has two `<audio>` elements in the footer, `audio.library-audio`, that swap roles. One plays (`data-role="active"`) while the other holds the next track (`data-role="standby"`). The previews' element is separate and never involved.

The next track starts loading when the playing one has `PRELOAD_LEAD_SECONDS` (15) left, or straight away for a track shorter than that. It is loaded into the standby element from `/api/player/stream/{id}`, and the choice is kept: shuffle picks at random, so the song that was loaded has to be the song that plays. Repeat one loads the same track again, so a looped track is gapless too, and repeat all loads the first track from the last. Anything that could change what is next drops the loaded track and loads the new one on the next timeupdate: a queue edit, and switching shuffle or repeat. Playing a preview drops it too. On a metered connection (`navigator.connection.saveData`) the standby element gets `preload="metadata"` and nothing beyond it, so the track starts the way it did before this existed.

The handover happens inside `loadLibrary`, which every route to a new track goes through: the end of a track, Next, and picking a row of the queue. It hands over only when the track asked for is the one the standby element holds, and only for a track that starts at once from the beginning, so a restored queue and a scrub are loaded as before. Where the stream's length agrees with the library's (within 2 seconds), a timer starts the standby element 40 ms before the end, since the `ended` event arrives late and a live album or a mix would carry the gap into the music. Otherwise the `ended` event does the same handover. If the standby element could not load its track, or the browser refuses to start it from a script (iOS does until an element has been started by a tap), the track is loaded into the playing element the ordinary way, and the second case stops preloading for the rest of the session.

The timer is kept by a Web Worker, not by `setTimeout` on the page. A hidden tab, which is where most listening happens, holds page timers to about one a second, so a page timer for a wait of 400 ms fires up to a second late and `ended` takes over with a small gap; a worker's timers are not held to that while audio plays. The rule and the arithmetic are in `frontend/src/handover.ts` (`handoverDelay`, `lengthsAgree`), the worker is `handover-worker.ts` and the page's side of it is `handover-clock.ts`. The clock is made on first use and the worker is started when the standby element begins loading, well before the last second, so it is ready when the wait is armed; the first `arm` never pays for loading it. Nothing about it is on the main bundle's critical path, since Vite builds the worker as a file of its own, fetched from the same origin the CSP already allows.

The wait is worked out from the playing element's `currentTime` and `duration`: real time to the end is what is left divided by `playbackRate`, less the 40 ms lead. It is armed only inside the last second and only while the element is playing, and it is worked out again on every timeupdate and on seek, play and rate change, each of which replaces the wait before it. A pause, a load of any other track and a discarded preload cancel it. Every wait carries a token, and the worker's answer for a token that is no longer current is ignored, so a wait made for one track can never start the next one. When the worker answers, the player checks again that the track and element are the ones the wait was made for, that the element is not paused and that it is still inside the last second. Where workers are unavailable, or one fails to start, the same wait is kept with `setTimeout`, which is right in a visible tab and late in a hidden one, and `ended` remains the safety net in every case.

What follows the song rather than the element, and is set at the handover: the queue index and the saved queue position, the scrobble (the submission for the track that ended, then now playing for the new one), the play history, the Media Session metadata and position state, the seek bar and length, and the visualizer feed (see [the visualizer note](visualizer.md#the-two-library-elements)). Only the element in play is listened to: the standby element's load, length and errors change nothing on screen until it takes over. Previous restarts the track after 4 seconds of playback and goes to the previous track before that, as before.

The suite checks the mechanism (what loads where, what takes over, what is reported) but cannot hear the join: headless browsers have no audio output to listen to. Check it by ear on a live album or a mix, in the browsers you use, when this code changes.

## Crossfade

Off by default. Set under Your settings, [Playback](settings.md#playback), from 1 to 12 seconds (`musimo.crossfade`), it overlaps the tail of one library track with the head of the next, using the same two elements as gapless playback. It reads `frontend/src/crossfade.ts` for the rule, `frontend/src/fades.ts` for the curves and `frontend/src/crossfade-settings.ts` for the stored value.

It starts from `maybeCrossfade` on the playing element's timeupdate, once all of this holds: the standby element has loaded the next track far enough to play (`readyState` of `HAVE_FUTURE_DATA` or more, so a metered connection, which loads metadata only, never crossfades), no sleep timer ends after this track, and `crossfadeSpan` says the join is due. `crossfadeSpan` returns 0, leaving it to gapless playback, for repeat one and for consecutive tracks of one album (the next song is queued straight after the playing one and shares its album). The wrap from an album's last track to its first under repeat all, and the same album queued out of order, do crossfade. The overlap is the setting, capped at half of either track, and once it is due it is never longer than what is left of the playing track, so a late start still ends when the track does. If the next track is not ready in time the ordinary handover does the join.

At the start of the overlap the new track takes over everywhere at once, by the same route as any handover (`finishTrack`, then `loadLibrary`): the queue index and saved queue position, the scrobble (the submission for the track that is ending, then now playing for the new one), the Media Session metadata and position state, the seek bar and the visualizer feed. The old track is not paused. Its element keeps playing as `fadingOut`, still marked standby, and is not touched by preloading until it is done. Every 100 ms the two levels are set on top of the volume and ReplayGain, on equal-power curves (`fadeOutGain` and `fadeInGain`), so the join holds one loudness. When the old track's element is out of sound it is paused. Its own events (pause, ended, timeupdate) are ignored like any standby element's.

Anything else that loads a track ends the overlap: Next, Previous when it goes back a track, a row of the queue, a preview or Close. Pausing during it cuts the old track and pauses the new one, rather than freezing two. If the browser refuses to start the standby element from a script, the old track is cut for the new one as in gapless playback.

Like gapless playback, the suite checks the mechanism but cannot hear the join. Check it by ear when this code changes.

## Sleep timer

The Now Playing control row has a Sleep timer button, a moon icon that opens a menu (`frontend/src/sleep-timer-control.tsx`): Off, End of track, End of album or queue, and 15, 30, 45 or 60 minutes. The running choice is checked. While one runs, the moon is accented and the time left shows beside it, in tabular figures, with a button to cancel it (choosing Off does the same). It is an icon, not a select, so the control row stays on one line at laptop widths. The menu opens upward and works like the row menus: Enter or Space on the button opens it on the running choice, the arrow keys, Home and End move, Escape closes it and returns to the button, and a click elsewhere closes it. A timer is not saved: a reload clears it, and so does closing the player.

- **End of track** stops after the track that is playing. Skipping to another track moves it to that track.
- **End of album or queue** stops after the last track in the queue, which for an album is the end of the album. What is queued is followed as it is edited. Shuffle and repeat never reach a last track, so the menu item is disabled while either is on (it says "Not with shuffle or repeat"), and turning one on cancels a timer that was set ("Sleep timer cancelled. Shuffle and repeat never reach the end of the queue."). Its time left is the rest of the track plus the songs still to come.
- **Minutes** counts real time, so pausing does not stop it. A preview leaves it running; a preview does clear the two end timers, which have no end to wait for.

The last five seconds are a fade to silence (`SLEEP_FADE_SECONDS`, `rampDown`) applied on top of the volume and ReplayGain, then playback pauses and the level goes back to normal. For the end timers the fade is the last five seconds of the final track. `finishTrack` reports the listen as for any finished track (scrobble submission and history), pauses, and loads the track that would have come next without playing it, so pressing play carries on from there and the saved queue points at it. With nothing next, the last track stays loaded and paused. For a minutes timer the pause can come in the middle of a track or a crossfade, and both elements are paused. The pause goes through the ordinary pause event, so the saved queue position and the Media Session state are updated as for any pause. The status line says "Sleep timer ended. Playback paused." No crossfade starts out of a track that a sleep timer ends after.

The player context exposes `sleep` (the choice and the seconds left, or null) and `setSleep(choice | null)`. The types and the menu's values are in `frontend/src/sleep-timer.ts`.

## Tracks that cannot be played

When a library track errors, the player skips to the next one and says which in its status line: "Skipped Delta, it could not be played". The next track follows the same rules as Next, so shuffle and repeat all apply. After `MAX_FAILURES` (3) tracks fail in a row the player stops and says so ("Stopped after 3 tracks in a row could not be played. Check the connection to Navidrome."), because that many in a row more likely means Navidrome cannot be reached than that every song is broken. A track that starts playing clears the count, as does starting a new queue. A queue restored on page load that starts on a broken track skips past it without starting playback. A track that only failed to preload is not skipped for that: it is loaded the ordinary way when its turn comes, and skipped then if it still fails. Repeat one does not retry a broken track, since that would never end.

## Play history

Each library track that actually played is recorded in a history kept in this browser only, under `musimo.play-history` (`frontend/src/play-history.ts`). A track counts once it has played past 10 seconds, or to its end when it is shorter than that. Catalog previews are never recorded, and neither is a saved queue that only restored its position: the element has to be playing. The list is newest first and capped at 200. A track is not recorded again while it is the most recent entry, so repeat one and replaying the same song add one row. Each entry keeps only what a row and a replay need: id, title, artist, album, duration, the cover and artist and album ids, its ReplayGain tags (so a replayed song is levelled) and when it played. Storage that is missing, blocked or unreadable is treated as an empty history, and a failed write is ignored.

The History tab on Now Playing lists the entries with the time relative to now ("5 minutes ago", "yesterday"), refreshed each minute while the tab is showing. A row plays that track again. With a queue loaded it slots in straight after the playing song and plays, so looking back does not throw away what was lined up; with nothing loaded it becomes a queue of one whose source is `history` ("Playing from your history"). A row has the same More actions menu as other song rows, with Play next and Add to queue. Clear history asks for confirmation, then empties the list and the stored copy. The player context exposes `history` and `clearHistory()`.

## About this track

The About tab on Now Playing says what the library holds for the playing track, since the reason to self-host is owning the files. It draws nothing for what Navidrome does not send: a row with no value, and a section with no rows, are left out, and a zero for bit depth, bitrate, sample rate, size, year or a track number counts as "not known". Its details are a bonus, so a failed read shows less and never an error.

- **File**: format (the file's extension, or the content type's subtype), bitrate, sample rate, bit depth, channels (Mono, Stereo, or a count), size and the path as Navidrome reports it, relative to the library.
- **Release**: album, year, label, genre, track and disc number, and contributors grouped by role ("Producer", "Performer (bass)"). The song's own tags win over the trimmed copy the queue carries. The label is the album's `recordLabels`.
- **Listening**: play count (when above 0) and last played, from Navidrome's `playCount` and `played`. Last played is relative to now, with the full date in its tooltip.
- **More you own**: up to 8 other albums by the track's artist, newest first, each linking to its Library page, and the rest of the playing album (up to 10 songs, then "and N more"). "Open album" beside the second goes to `/library/albums/{id}?track={song}`, and the album page marks that song as playing (`aria-current`, the playing row's background) and scrolls it into view, even when the queue was not started from that album. The `track` search parameter is read as text, because the router turns a value of only digits into a number.
- **Look for a better version**: for a lossy file (mp3, aac, m4a, ogg, oga, opus or wma) with a bitrate known and under 192 kbps (`LOW_BITRATE_KBPS`), a quiet link to Search for "artist title". A lossless file, or one with no known bitrate, never gets it. M4A counts as lossy because it is nearly always AAC; an ALAC file in one has a bitrate far above the threshold.

The song comes from `GET /api/player/song/{id}`, which passes Navidrome's whole song through, so no field list has to grow. The trimmed track fields (`TRACK_FIELDS`) stay as they were, since they are kept for every song in the library. The one-line summary under the artist reads the same query (`['player-song', id]`), so opening the tab costs no second request. The album and artist reads use the query keys the Library pages use, and wait until the tab is showing. The rules and wording are in `frontend/src/track-info.ts` and the tab in `frontend/src/about-track.tsx`.

## Waveform seek bar

The seek bar on the Now Playing page draws the track's peaks in place of a line: one centred bar to each 4 pixels of the bar's measured width, the played part in the accent, the rest in the muted token at 60% (`fill-accent`, `fill-muted/60`), and a 2 px playhead in the accent. Every colour is a theme token, so a theme repaints it with no drawing code. The footer player, the phone mini player and the full screen and popout controls keep the plain range.

The range input is still the whole control. The peaks are drawn behind it and the input is made invisible over them, so the keyboard (arrows step 0.1 seconds, and the page's own keys leave a focused slider alone), the pointer (click and drag), the disabled state and the accessible slider (`Playback position`, with its value and maximum) are the browser's own and unchanged. The one thing the box takes over is the focus ring, which an invisible input cannot draw. The thumb is given no width so the input's travel is the whole box and a click lands where the playhead is drawn. It is the same element with or without peaks, so a focus in progress survives them arriving, and the box is 32 px tall either way so the controls under it do not move.

While the peaks load, and whenever there are none (a 404 or 503, a network error, a body with fewer than two peaks), the bar is the plain range and nothing on the page says anything went wrong. The component and its query (`['player-waveform', id]`, kept while cached, no retry) are `frontend/src/waveform-seek.tsx`. The arithmetic (how many bars fit, folding the peaks to that many by the loudest in each, the SVG path) is `frontend/src/waveform.ts`.

### Where the peaks come from

`GET /api/player/waveform/{id}` (`backend/waveform.py`) returns `{"peaks": [...]}`: 800 values from 0 to 1, the loudest in the track being 1. A peak is the loudest sample in a 12.5 ms window of the first audio stream, decoded by ffmpeg to 8 kHz mono, and the windows are folded to 800 points by their loudest, so the result does not depend on the length Navidrome reports. A track under 800 windows repeats them. Values are stored as one byte each and sent to three decimals.

- **Source.** The song is read from Navidrome (`getSong`) for its `path`. If that path, relative or absolute, resolves to a file inside a library root (`MUSIMO_LIBRARY_ROOTS`, after `..` and links are resolved, so a path cannot leave the root), ffmpeg reads the file there. Otherwise Musimo copies Navidrome's stream into a temporary directory (at most 512 MiB) and ffmpeg reads the copy, which is deleted afterwards. A copy rather than a pipe, because some formats cannot be decoded from one, and rather than a URL, which would put the Subsonic token on ffmpeg's command line. ffmpeg's error output is discarded, since it can carry a path.
- **Cache.** The SQLite `waveforms` table holds one row per song: the id, a fingerprint and the peaks. The fingerprint is the algorithm version plus, for a file on disk, its size and modified time in nanoseconds, or for a stream Navidrome's size and `updated` (`created` when there is none). A request whose fingerprint differs from the row's is decoded again and replaces the row, so a retagged or replaced file is picked up and rows do not pile up. A hit costs one `getSong`, one `stat` and one read.
- **Queue.** One decode runs at a time and up to 8 requests wait behind it (`QUEUE_LIMIT`), so a big album does not start twenty ffmpeg processes. A ninth is refused with 503 and `Retry-After`. A request that waits longer than 30 seconds (`QUEUE_WAIT_SECONDS`) gives up with 404. Once it has its turn a request checks the cache again, so two requests for one track decode it once.
- **Timeout.** A decode is stopped after 60 seconds (`DECODE_SECONDS`): ffmpeg is killed and the request is 404, never left hanging. A file ffmpeg cannot decode, a stream over the limit and a missing ffmpeg are 404 too. Those failures are remembered in memory (256 tracks, until a restart or until the file changes), so a broken file is not decoded again on every visit.
- A failure reaching Navidrome is the usual 503, and the item id is checked like every other route's.

## Volume levelling

Library tracks are levelled with ReplayGain when Navidrome reports it. OpenSubsonic songs carry an optional `replayGain` object (`trackGain` and `albumGain` in dB, `trackPeak` and `albumPeak` as a fraction of full scale). The backend keeps it in the trimmed track fields (`TRACK_FIELDS` in `backend/navidrome.py`) and passes it through unchanged on album, playlist, queue and artist responses, and the browser reads it as an optional `replayGain` on `libraryTrackSchema`. A file with no tags has no `replayGain` and plays unchanged.

The maths is in `frontend/src/replay-gain.ts` and has no player state in it. `replayGainMultiplier` turns a track's tags, the mode and the pre-amp into a factor: Off gives 1, Track uses `trackGain`, and Album uses `albumGain` while the track is `playsAlbumInOrder` (shuffle is off and the song before or after it in the queue is from the same album), else `trackGain`. Album mode also falls back to `trackGain` when a file has no `albumGain`. The pre-amp is added to a track that has a gain; a track with no usable gain is never touched. The factor is capped at 1 / peak, using the peak that matches the gain in use, so the loudest sample cannot pass full scale.

The player applies the factor to each audio element's `volume` (`outputVolume` and `applyVolume` in `frontend/src/player.tsx`), on top of the volume the person set. The `volume` state, the slider and `musimo.player-volume` are never changed by levelling, so the slider reads what they set. The standby element is levelled for the track it has preloaded, so a gapless handover arrives at the right volume, and an element finishing its last moments is not touched. It is re-applied when the setting, shuffle, the queue or the playing track change. Previews are not levelled.

An audio element's volume tops out at 1, so a boost only shows while the slider leaves room for it, and a quiet track at full volume cannot be raised. Cuts always work.

The mode and pre-amp are per-browser settings; see [Playback](settings.md#playback). Musimo does not write ReplayGain tags when it downloads yet, so only files tagged elsewhere are levelled.

## API

- `GET /api/player/capabilities`: connection and server version.
- `GET /api/library/albums`: whole-library album browsing. `q` (album or artist name), `sort` (newest, title, artist or year), repeated `genre` and `year`, `offset` and `size` are applied on the server, which returns the page, the matching `total` and the `genres`/`years` present across the library. It shares the album walk described under artists below.
- `GET /api/library/artists`: whole-library artist browsing. `q`, `sort` (name, albums or recent), repeated `genre` and `year`, `show` (favourites, played or unplayed), `offset` and `size` are applied on the server, which returns the page, the matching `total` and the `genres`/`years` present across the library. Navidrome cannot filter artists this way, so the server walks every album once (500 at a time, cached for 60 seconds and dropped after a scan) and describes each artist by their albums: an artist matches a genre or year if any of their albums, shared ones included, carries it; recent is their newest album's added date; played means any of their albums has a play. Favourites are Navidrome stars.
- `PUT` and `DELETE /api/library/artists/{id}/favourite`: star and unstar an artist in Navidrome.
- `GET /api/library/tracks`: whole-library track browsing. `q`, `sort`, repeated `genre` and `year`, `offset` and `size` are applied on the server, which returns the page, the matching `total` and the `genres`/`years` present across the library. Supported sorts are title, artist, album, year, duration and newest.
- `GET /api/library/tracks/search`: one upstream page of matches, for the playlist song picker.
- `GET /api/library/tracks/selection`: the same filters without paging, for Play all and Shuffle. `shuffle=true` returns a server-side random sample; `limit` is capped at the same 500 songs the saved play queue accepts.
- `GET /api/player/song/{id}`: song details for a single track, passed through whole. The About tab reads its file facts (`suffix`, `bitRate`, `samplingRate`, `bitDepth`, `channelCount`, `size`, `path`), listening record (`playCount`, `played`), tags and `contributors` from it. `GET /api/library/albums/{id}` passes `recordLabels` through the same way.
- `GET /api/library/playlists`: playlists visible to the configured account, plus `liked_id` for the linked playlist. Identifying it here is a plain read and never creates one.
- `GET /api/library/playlists/liked`: reads the stored link from SQLite `linked_playlists`, adopts an existing playlist named Liked when none is stored, otherwise creates one, and clears a dead link.
- `GET /api/library/albums/{id}`, `GET /api/library/artists/{id}` and `GET /api/library/playlists/{id}`: detail resources.
- `GET /api/library/artists/{id}/tracks`: all unique tracks from the artist's albums, fetched with bounded concurrency for Play all and Shuffle.
- `POST`, `PATCH` and `DELETE /api/library/playlists`: create, rename and delete playlists. Deleting the linked liked playlist is refused with 409. `POST /api/library/playlists/{id}/songs` adds a song or removes it by its current playlist index.
- `GET /api/player/stream/{id}`: proxied audio. A single valid byte range is forwarded and Navidrome's safe media headers are preserved.
- `GET /api/player/art/{id}`: proxied cover artwork. Navidrome answers an item it does not have with a JSON error and status 200; that is refused with 503 rather than passed on as a picture. An artist picture that is Navidrome's no-photo star (recognised by its hash in `backend/navidrome.py`) is replaced with that artist's newest album cover that is real art; if none has any, the star stays.
- `GET` and `PUT /api/player/queue`: restore and save the Navidrome play queue. `PUT` takes `ids` (at most 500), the `current` id, which must be one of them, and the position in milliseconds. Every queue edit sends one.
- `POST /api/player/scrobble`: report now playing and completed listens.
- `GET /api/player/lyrics/{id}`: Navidrome structured lyrics with an LRCLIB fallback. Each line's `start` is in milliseconds, and an item's `synced` says whether its lines are timed. Now Playing follows timed lines from the player's position, in the Lyrics tab or in the large lyrics view that takes over the content area with the track's transport in a strip along the bottom; see [Lyrics](now-playing-popout.md#lyrics).
- `GET /api/player/waveform/{id}`: about 800 normalized peaks (`{"peaks": [0.12, ...]}`) for the Now Playing seek bar, worked out once with ffmpeg and cached in SQLite until the file changes. 404 when there are none or the wait or decode timed out, 503 with `Retry-After` when the line for the decoder is full. See [Waveform seek bar](#waveform-seek-bar).

## Playback details

Space toggles library playback as well as previews, everywhere but a text field, select, button or link. The Now Playing page adds its own keys, on top of that: left and right arrows seek five seconds, Shift with either goes to the previous or next track, up and down arrows change the volume, M mutes, L opens the lyrics tab (and again, the large lyrics view, which Escape or L closes), Q opens Up next, and `?` opens a cheat sheet dialog listing these and the stage's keys. They are not taken from a text field, select, slider, tab list or menu, or while a dialog such as the command palette is open, and while the stage is full screen or focused its own keys are the ones that act, so nothing is done twice; see [the popout note](now-playing-popout.md#keyboard). The Now Playing stage supports F for full screen, Esc to leave full screen or close the popout, left and right arrow keys to seek by five seconds, up and down arrows to adjust volume, M to mute, N and P to skip tracks, V to switch between artwork and the visualizer, H for the visualizer's debug overlay, and `[` and `]` to walk the visualizer's presets. N and P are the transport, so the presets take the brackets beside them. The stage's top bar chooses the preset and how large the scene's simulation is. It also chooses which scene draws, though that select is hidden while there is only one of them.

Library playback is analysed for the visualizer. Every `play` event on a library element hands that element to `attachAudio` (`visimo/audio`, loaded on demand), which builds one `AudioContext` the first time, resumes it and routes the element through one `AnalyserNode`. Both library elements have to reach that same analyser, so the visualizer keeps drawing after a handover; see [the visualizer note](visualizer.md#the-two-library-elements) for what that asks of the package. The source is only attached once the context is running, so a suspended context can never silence the track; if the browser suspends it later (a hidden tab, another app taking the output on iOS), the next play or the tab becoming visible again resumes it. Previews are never attached: they stream from provider CDNs without CORS headers, and a media element source on such audio is silenced for good.

Persistence uses browser storage keys `musimo.player-volume`, `musimo.player-shuffle`, `musimo.player-repeat`, `musimo.library-layout`, `musimo.now-playing-view` (artwork or visualizer), `musimo.now-playing-tab` (up-next, lyrics, about or history), `musimo.play-history` (see [Play history](#play-history)), `musimo.replay-gain` (off, track or album) and `musimo.replay-gain-preamp` (dB; see [Volume levelling](#volume-levelling)), `musimo.crossfade` (seconds, 0 is off; see [Crossfade](#crossfade)), `musimo.lyrics-offset` (a timing nudge per track, at most 200), `musimo.visualizer-preset` (plume or wash), `musimo.visualizer-scene` (fluid), `musimo.visualizer-fluid-grid` and `musimo.now-playing-visualizer-notice` (the no-WebGPU notice has been shown). The queue autosaves every 10 seconds of playback and on pause or close. Now playing scrobbles on play and submits on track end. Previous restarts the current track after 4 seconds of playback. Repeat one is available. MediaSession handlers provide play, pause, next and previous, and the session's metadata and position state (duration, position, rate) follow the element in play, refreshed on load, play, pause, seek and a length change and at each handover.

Now Playing is for library tracks only. While a catalog preview plays, the page says "A preview is playing." and that Now Playing and its visuals play with tracks from your library; with nothing loaded it says "Nothing playing yet."

Every item ID is length and character checked before it reaches Navidrome. The proxy forwards only a small media-header allowlist. Upstream errors become a generic 503 response without exposing the private address or credentials.

Navidrome does not expose standard API calls for deleting songs, albums or artists. Musimo therefore does not show destructive media actions in Library. Remove files through the storage or Navidrome administration workflow, then let the library scan reconcile the index.

## Verification

`tests/test_player.py` covers capability discovery, library and player routing, repeated queue IDs, credential isolation, item-ID validation, safe response headers, artwork, a missing item or a compressed answer not being passed on as broken media, the album-cover stand-in for an artist without a photo and a ranged audio response. It covers album browsing (search by album or artist, the four sorts, genre and year filters and whole-library facets) and artist browsing too: genre, year, played and favourite filters worked out from the artists' albums, the three sorts, one album walk shared across calls and a new one after a scan, and starring and unstarring. It also covers server-side track filtering, sorting, paging, facets, shuffle, the trimmed song fields (ReplayGain kept when Navidrome sends it, absent when it does not), the song's file and listening fields and an album's record labels passing through untrimmed, the reused track cache and its single-flight walk, and that listing playlists reports the linked liked playlist without creating one and refuses to delete it. It also checks that a queue of 500 songs is saved and one of 501 is refused. The queue editing helpers (the 500 song limit, where Play next lands, where the playing track ends up after a move, and which songs shuffle plays first) are unit tested in `frontend/src/player.test.ts`, which also covers when the next track is due to load and the wording of the skip and stop notices, the handover's wait (inside the last second only, the lead, playback rate, the stream-length guard) in `frontend/src/handover.test.ts`, the history's ordering, de-duplication and cap and the relative times in `frontend/src/play-history.test.ts`, the gain maths (mode choice, pre-amp, the peak cap, album order) in `frontend/src/replay-gain.test.ts`, the crossfade rule and stored value in `frontend/src/crossfade.test.ts`, the fade and crossfade curves in `frontend/src/fades.test.ts`, the sleep timer's choices in `frontend/src/sleep-timer.test.ts`, the About tab's formatting, rows and lossy rule in `frontend/src/track-info.test.ts`, `frontend/e2e/about.spec.ts` (the summary line, the sections, the search link, the marked song on the album page and a tab with nothing known), `frontend/e2e/gapless.spec.ts` drives the standby element loading the next song and taking over, the same in a tab faked as hidden with the page's timers frozen (the standby element must start before the playing one reports `ended`), the metered-connection case, a skipped song and the stop after three failures, and `frontend/e2e/queue-editing.spec.ts` drives the menus, Up next's buttons, keyboard and drag, Save as playlist and the 500 song refusal in a browser. Frontend type checking, linting and production builds cover the browser contract. A live credentialed Navidrome playback check remains required for each installation.

`tests/test_waveform.py` covers the waveform route: a file in the library decoded once and then served from the cache, a changed file (a new size, or a new modified time at the same size) and a changed stream (`updated`, `size`) decoded again over the same row, a path that climbs out of the root falling back to the stream and the stream copy being deleted, one decode at a time across five requests, one decode for the same track asked twice, a full line refused with 503, a wait that runs out and a decode that runs out both answering 404 with ffmpeg stopped and the turn handed back, a broken file or an oversized stream not being retried, and an unknown song and a bad id. The peak arithmetic (split reads, folding, silence, a short track) is unit tested, and a real ffmpeg decode of a quiet second and a loud one runs when ffmpeg is installed. `frontend/src/waveform.test.ts` covers the bar arithmetic. `frontend/e2e/waveform.spec.ts` drives the seek bar against a routed waveform: the bars drawn behind one slider, the keyboard and a click seeking as before, the accent and muted layers following the theme tokens, the plain bar while loading (with focus kept) and when the server has none, is busy or sends too little, the footer keeping the plain bar and the phone width. It cannot judge how the bars look, so look at them on a real track when the drawing changes.

Track browsing gathers pages from Navidrome up to a bounded cap and reuses them for a short window, so filters, sort and totals describe the library rather than one page. Each song keeps only the fields the browser reads (a full Subsonic song is about 4.5 KB), which puts a 10,873-song library at about 16 MB. Beyond the cap they describe the first 50,000 songs Navidrome returns. Concurrent callers share one walk, and a scan started by Musimo clears the snapshot so a new download appears without waiting out the window; a scan started from Navidrome's own interface waits for it.
