# Library player

The player reads the music folders Musimo already indexes. Those files supply playable ids, library browsing, audio streams, cover art, lyrics, play counts and the saved play queue.

## Configuration

Point `MUSIMO_LIBRARY_ROOTS` at the folders that hold the music. The capability endpoint reports an unavailable state when none of those folders is mounted and readable, instead of failing the request.

### Import listening state from Navidrome

`python -m backend.library.import_navidrome SOURCE TARGET --user USER --root "SOURCE_ROOT=TARGET_ROOT" --report report.json` reads both SQLite files without changing them. The source root is Navidrome's library path; the target root must already be enabled and scanned in Musimo. Repeat `--root` for multiple libraries. Windows source paths can map to Linux container paths. Use consistent database backups for the first run, and keep the report outside Git because it lists unmatched personal library paths.

The importer targets the Navidrome 0.63.2 schema. It matches existing source tracks by path, then by artist, album, title and duration within one second only when exactly one target fits. It imports the selected user's manual playlists, song likes, artist favourites, larger play counts and later last-played dates. Other users and smart-playlist rules stay out. Playlist order and repeated songs survive. Existing playlist names are skipped and reported, including an existing playlist named Liked; song stars still go into Musimo's linked liked playlist. A playlist or queue over 500 matched entries is reported and skipped rather than truncated. An existing Musimo queue is preserved. With one name, the import lands on that name. With more than one, pass `--listener` with the name or the id. With none, it lands on the shared rows, as before.

Review the dry-run report, back up Musimo, stop its service, then repeat with `--write`. Run the command where the target database is accessible and restart Musimo afterward. Writes and an import summary commit in one transaction; failures roll back. Repeating the import does not duplicate likes or playlists. Missing artist names are reported rather than creating favourites that cannot be browsed. The importer does not copy audio or change song ids.

The queue decoder follows Navidrome's [stored comma-separated ids and current index](https://github.com/navidrome/navidrome/blob/v0.63.2/persistence/playqueue_repository.go). Playlist ordering follows its [playlist_tracks.id](https://github.com/navidrome/navidrome/blob/v0.63.2/persistence/playlist_repository.go). A source without a playqueue table is reported as having no source queue.

## Ids

A song id is `tr-` plus 16 hex characters, stored on the file's row. The same path keeps that id across rescans and tag edits. A moved or renamed file is a new song: the old path is gone, so the playlist entries, play counts and queue rows that used its id go with it.

Album and artist ids are not stored. An album id is `al-` plus 16 hex characters, a frozen hash of the album artist and the album name. An artist id is `ar-` plus 16 hex characters, a frozen hash of the artist name. The hash is `frozen_id` in `backend/library/player.py` (the prefix `musimo-id-v1`), not `normalize()` from `backend/core/text.py`, which ownership matching shares and will keep changing. The same names keep the same id across rescans. A retag that changes the album or artist name is a new id, and a favourite on the old artist name is lost.

## Player experience

Library has Home, Albums, Artists, Tracks and Playlists views. Each view and detail page has its own URL, so refresh and browser Back preserve page navigation. Albums opened from an artist use `/library/artists/{artist}/albums/{album}` and return to that artist. An artist's All songs view uses `/library/artists/{id}/songs`. One search field searches the active view; album, artist and track searches run against the library, while the smaller playlist list is filtered in the browser. Sort choices are specific to each view. Search, sort, genres, years and Show are kept in that view's address, so a refresh keeps them. The browser also remembers the last choice for each view for the rest of the visit, and a view tab or the back link opens it again. More results load as you scroll. Grid and list layouts are available for collection views and the choice is remembered in the browser. Artist images come from the library. Artist, album and playlist rows can open, play or shuffle their collection. On album cards, the artwork play button starts the album while the remaining card opens its songs. Album cards and rows carry the release year. Opening an album or playlist reveals its tracks, and Play all and Shuffle both create one persistent queue. The footer player provides seek, previous, next, shuffle, repeat, volume and mute. Its artist and album names open their Library pages, and the cover thumbnail opens Now Playing. On a wide window an expand icon sits among the buttons as a second click target; it is hidden from the tab order and the accessibility tree, so the cover is the one "Open Now Playing" link for a keyboard or a screen reader. While a library track plays, the cover wears a slow accent ring as a hint that there is more behind it; the ring goes away when paused and holds still under `prefers-reduced-motion`. A catalog preview's cover is only a picture. While playing a library track, a thumbs up button toggles membership in the default linked playlist, and a plus button opens a playlist picker. The queue and position restore from the library after a refresh. Browser media controls receive the current title, artist, album and artwork.

In the Listening room layout (`musimo.layout` = `room`) the footer is never shown: it stays in the page only for the audio elements it holds, and `features/player/player-dock.tsx` draws the controls instead. A wide window gets the dock, a column right of the page with the cover, title, like, a mini waveform seek bar, the transport, volume, the sleep timer, add to playlist, close, and Up next (play a row, move it by its handle, Alt with an arrow key or its buttons, remove it, clear the queue, save it as a playlist). Under 1100px the dock becomes a 76px bar under the page, with Up next in a panel that opens above it. A phone gets a floating mini player above the tab bar that opens Now Playing. The dock and the mini player step aside on Now Playing while a library track plays, as the footer does. A failed queue save shows as a strip at the head of Up next with Retry, and as a toast; a retry that lands clears both.

On a wide window the footer is 76px tall in three columns of 1 : 1.3 : 1. The left has the cover (the link to Now Playing), the title, "artist · album" and Like. The middle has shuffle, previous, play or pause, next and repeat, with the time, seek bar and length under them. The right has Add to playlist, Queue (a link to Now Playing, where the queue is), mute and volume, an expand link to Now Playing and Close. Messages the player has for you (a queue that could not be saved, a song it skipped, "Added to the queue") are toasts, not a line in the footer; a failed queue save has a Retry button. On a phone (under 768px wide) the footer is a mini player: a rounded card (radius 12) floating 6px above the tab bar, with the artwork, title and artist, play or pause and next at 44px, close, and a 2px seek line along its top edge. It is hidden until something plays, and again while Now Playing shows a library track, since the page there repeats its title, play or pause, next, close and seek bar. Previous, shuffle, repeat, like and mute are on the Now Playing page, which the artwork or the title opens, and Now Playing offers Add to playlist in place of the footer's plus button. Volume is left to the device's own buttons. A catalog preview gets the same row with play or pause and close.

Any play button becomes a pause button while the thing it starts is the thing playing. For a track that means the track itself; for an album, artist, playlist or the Tracks list it means that collection still owns the queue. Pressing pause again resumes playback rather than refetching.

Albums (and Home), Artists and Tracks run search, genre and year filters, sort order and the match count on the server, so they describe the whole library rather than the pages this browser has scrolled through. On Tracks, Play all and Shuffle do too. Play all plays the first 500 songs in the current sort order, because one saved queue holds 500 songs. Shuffle plays every matching song once, in a random order, and ignores the sort. When that fits in the queue it plays straight through, and repeat plays it again. When it does not, the queue holds a window of at most 500 and the player asks the server for the next window as it plays. The server keeps that order under a seed for a day (refreshed each time the player asks for more). The browser stores the seed and a cursor in `musimo.shuffle-deck`, one copy for each name. The song ids stay on the server. A later pass leaves out songs still in the queue. Editing the queue by hand clears the deck. If Musimo restarts, or a day passes with nothing playing, it forgets the order: the songs already queued still play, and Shuffle again starts a new pass. Past a million songs the shuffle refuses rather than returning a short one. Playlist sorts and the playlist visibility filter still work on the loaded list.

On a desktop the list views carry one toolbar: the search field, the sort menu, the genre and year menus (and Show on Artists, the public or private filter on Playlists), the loaded count and the grid or list toggle. On a phone (`usePhone` in `frontend/src/lib/use-phone.ts`, the same 768px edge as `max-phone:`) that toolbar is one row, the search field and a single Filter button, so the first album is on the first screen. Filter opens a bottom sheet (the shared `ReviewDialog`, a native modal `<dialog>`) holding Sort, Show where the tab has it, Genres and Years (open in the sheet's flow rather than floating), the grid or list toggle for every tab but Tracks, and Clear filters. The button reads "Filter (2)" while two filters are on, counting genres, years, Show and the playlist visibility; the sort and the layout are choices, not filters, so they are not counted. The sheet closes with Done, Escape or its close button. The loaded count is not in the sheet: on a phone it reads under the list. The page heading shrinks to the small heading size (`PageTitle compact`) and keeps its readiness tag on the same row. On Playlists the New playlist button gets its own row under the search row.

The album, artist and playlist pages open with one shared header (`CollectionHeader`, in `frontend/src/features/library/collection-header.tsx`) laid out like the catalog album page: a large cover, a small eyebrow, the title, a byline, a meta line, then the actions. A title stops after two lines. A phone puts a cover of about 104px beside the eyebrow, title, byline and meta line, and gives the actions their own row under both, so the first song is on the first screen even with the mini player loaded.

```text
desktop                                   phone
+-------+  ALBUM · 2018                   +------+  ALBUM · 2018
| cover |  Title                          |cover |  Title
|       |  Artist                         +------+  Artist · 2 songs · 7 min
+-------+  2 songs · 7 min · Ambient      [Play all] [Shuffle] [...]
           [Play all] [Shuffle] [...]     1  First song
                                          2  Second song
```

- **Album:** the cover from the library, the eyebrow "ALBUM · year" (just "ALBUM" when the year is unknown), the title, the artist as a link to that artist's Library page (plain text when the library sends no artist id), and a meta line of song count, total length and genre when there is one ("12 songs · 42 min · Ambient"). Actions are Play all, Shuffle and the Play next / Add to queue menu.
- **Artist and All songs:** a large round photo, the eyebrow "ARTIST", the name and a meta line of album and song counts ("2 albums · 3 songs"; the song count waits until the songs have loaded). Actions are Play all, Shuffle, Add to favourites and All songs / Albums. The All songs view keeps the same header.
- **Playlist:** a 2 by 2 mosaic when four different covers are on hand, otherwise the first song's cover (or the library's own playlist cover, or an icon), the eyebrow "PLAYLIST", the name, "By owner" when the owner is known, and a meta line of song count, length and "Public" or "Private" ("4 songs · 13 min · Private"). Actions are Play all, Shuffle, the queue menu, Rename and Delete (no Delete for the liked playlist).

Lengths in these headers read as "42 min" or "1 hr 4 min"; song rows keep the exact `m:ss`. The first column of a song row counts what suits the list (`numbering` on `TrackList` in `frontend/src/features/library/track-list.tsx`): an album's rows show each song's number on the album, a playlist's rows show their place in it (1, 2, 3, and so on, never the song's number on its own album), and the Tracks tab shows a number only in album order. Sorted any other way, such as Track A to Z, the Tracks tab drops the column, since a song's number on its own album means nothing beside songs from other albums. The album name in a row wraps to two lines and then stops, with the full name in its tooltip. On these three pages the browse heading (the view name and its count) and the view switcher are dropped, and a slim row carries the back link, so the content starts higher. The title is the page's `h1`. The list views keep their heading (smaller on a phone, as above). A page that fails to load shows its error and Retry without a header, since there is no title or cover to show.

An artist page sorts its albums by release date, title or play count, and its All songs view sorts by album order, title, play count, length or release date. A non-default order is part of that page's address, and coming back to the artist or to All songs restores it. The All songs URL (`/library/artists/{id}/songs`) survives refresh and returns the app shell. A popularity chart plots the library's play counts for the artist's dated releases, oldest to newest; it says so plainly when there are not yet enough recorded plays to draw a line.

Editions of one album share a card on the artist page. Albums group when their titles match after case, punctuation and trailing edition words in brackets or after a dash (Deluxe, Expanded, Remastered, Anniversary and the like, with years and ordinals beside them) are removed, so "Circles", "Circles (Deluxe Edition)" and "Circles - 2020 Remaster" are one card. Titles that only look alike ("Blue" and "Blue Moon") or carry a different tag such as "(Live)" stay apart, and a group of one is an ordinary card with its title untouched. A grouped card shows an "n editions" chip, opens a dialog listing each edition (oldest first) with its edition words, year and song count, and each row opens that album. The card's play, shuffle and queue actions use its lead edition, the plain album when there is one. For sorting, a group counts as one album: newest or oldest by its newest or oldest edition, and most played by all its plays. The header count reads "48 albums, 56 editions" when they differ and just "48 albums" when they do not. The grouping is `frontend/src/features/library/album-editions.ts`; the popularity chart still plots every edition, and the Artists list's album count still comes from the server. `frontend/e2e/library-controls.spec.ts` covers it with a fixture artist that has two editions of one album. A grouped card prints the span of its editions' years (`yearSpan`, "2015–2025"), because the group is placed by its newest or oldest edition and the lead's year alone would look out of order.

Each name has their own liked playlist. It is the one playlist Musimo maintains for that name, so it is always listed, sorts to the top of every playlist view, and has no delete control. Rename is available for all playlists including the liked playlist; only the delete control is refused for it. `DELETE /api/library/playlists/{id}` refuses it as well, because the thumbs up button depends on it existing. Its identity is the stored link, so the protection begins when Musimo adopts or creates the playlist rather than applying to anything a user happens to name Liked. Other playlists can be created, renamed, emptied and deleted; the delete control appears on hover or focus. Playlist rows show their song count and length and can be filtered by public or private. The playlist picker is a centred modal with a 25 row limit and filter box, opened from the footer player's plus button or from Now Playing's Add to playlist button. The dialog is rendered beside the footer, not inside it, so it still opens while the footer is hidden. The liked playlist is excluded from the picker. Inline New playlist is available with the current song. Each row shows whether the current song is already in that playlist and toggles between Add and Remove, so the same song cannot be added twice, and each row expands into a scrolling list of that playlist's songs where any of them can be removed. The playlist page also offers an Add songs search box. Playlist reads share one cache with the playlist page, so a change made in the player appears there without a reload.

Now Playing is also in the desktop sidebar, as the last row of the upper group (after the playlists), with the current cover as a small thumbnail in place of an icon. It exists only while a library track is loaded, and the spacer above Downloads absorbs it so its arrival or departure moves no other row. The phone bottom bar keeps its five items, which fill its 64px, so a phone reaches Now Playing from the mini player's cover or title.

Now Playing shows the artwork in a stage that can go full screen in the tab or pop out into a floating window (right-clicking it offers Go to album, Go to artist, Add to playlist and Full screen), over a soft wash taken from the cover's dominant colour and mixed into the theme's canvas so text keeps at least AA contrast; the artwork and the wash cross-fade over about 300 ms when the track changes, and cut under `prefers-reduced-motion` (see [the popout note](now-playing-popout.md#backdrop-and-track-changes)). Under the stage are the track's title and every control the footer has, and one panel of tabs, Up next, Lyrics, About and History, beside it (beneath on a phone). Under the artist line the page also sums the file up in chips (FLAC, 44.1 kHz, 1,012 kbps and the year); see [About this track](#about-this-track). The page has two layouts, Classic and the Listening room; see [the popout note](now-playing-popout.md#two-layouts). The seek bar between the two times draws the track's waveform, and the footer player keeps its plain bar; see [Waveform seek bar](#waveform-seek-bar). Up next lists what follows the playing track and, where the player knows the source of the queue, says "Playing from" its name. It is also where the queue is edited; see [Editing the queue](#editing-the-queue). The footer player is hidden while the page shows a library track, on a desktop and a phone, because the page has all of its controls, its close button included; the page repeats the footer's status line only for errors and confirmations, not for "Your music library" or "Queue restored". The footer publishes `--player-height` as `0px` for as long as it is hidden, so the queue dock and every other offset that adds it up sit where they would with no player; the height comes back when the footer does. See [the popout note](now-playing-popout.md). Musimo asks the library first, then checks LRCLIB when the library track has no imported lyrics. Catalog previews and library tracks have separate audio elements (the library has a pair, see [Gapless playback](#gapless-playback)), and only one of them plays at a time. The library element that is playing also feeds one Web Audio `AudioContext` for the Now Playing visualizer, butterchurn's port of MilkDrop; see [the visualizer note](visualizer.md) for why previews must never touch it.

## Editing the queue

### Music bot

The music bot is a pet, Octive by default, that perches on the player; tapping it opens the chat. The sidebar's Octive row and the top bar's Ask Octive pill open the same chat as a full page (`/music-bot`). The pet's popover, the phone sheet and the page share one conversation (`MusicBotProvider` in `frontend/src/features/music-bot/bot-chat.tsx`), so a chat carries between them. It searches existing artist, genre, year, duration, Liked playlist and play-history data. Genre words match the raw tags and the broad genres in [genre mapping](genre-mapping.md), so "hip hop" finds both Rap/Hip Hop and Hip-Hop. The server searches the genres and artists on the plan. It does not read the request text again. When more songs match than the request needs, the bot picks among them at random, so asking again gives a different set, and the summary says so ("Picked at random from 1,240 matches."). Play counts matter only when you ask about them (familiar, played or unplayed songs). Once a sound profile is on, "more like this" lists the closest songs first; on tags alone it picks at random like any other search. "More familiar" or "most played" picks from your most played songs and lists them most played first. In a library search, or when songs are added to a proposal, a repeated title by the same artist is kept once, and an artist fills at most two places unless the request names that artist (songs with no artist tag are not capped). Refining a proposal or the queue only filters it and keeps your order. Audio analysis is not enabled: the two recipe settings under Music bot in Settings are empty, so the bot refuses mood, energy, tempo, instruments and vocals, and "more like this" uses saved genre or artist tags, not a claim about how the recording sounds. The machinery that would change that is described in [song characteristics](audio-profile-spec.md); turning it on is a settings change after a listening check.

Generated selections are previews. Play starts that selection; Play next and Add to queue use the existing queue actions; Replace upcoming preserves the current song and its playback position. Each action confirms the stored revision of the proposal the card shows (see [Preview and confirm](#preview-and-confirm)), then checks the browser queue has not changed since the request began. The 500-song limit still applies. Save as playlist asks for a name and saves exactly the songs the card shows. A duration target includes whole songs and may run slightly over; unknown durations are excluded when there is a target. Too few matches leave a shortfall instead of relaxing exclusions.

Each result is a card that says "PREVIEW, NOT APPLIED" until an action is pressed, then "IN YOUR QUEUE" with Undo. It shows where it looked, the server's summary (what it is based on), one chip per active filter, what the songs add up to, the shortfall in minutes, the songs, and the total length. A list of 12 songs or fewer is shown whole. A longer one opens on about six songs the server picked to stand for it, and See all N songs shows the rest. Removing a chip sends a plain follow-up ("any year", "allow songs played today"), which goes through the model like anything typed. A song's More menu offers Use as reference, Play this song and Remove from this list. Play this song is the one action that does not go through a proposal: it is one song, played at once, and the server rechecks that id. Removing a song is a `remove` edit, the next revision of the same proposal, so what is confirmed is what the card shows and the removed song is not drawn again there. On a library search each song also has a Pin toggle (a button with a visible label, pressed or not), and the card has Another set, which keeps the pinned songs and draws the rest again (it reads Replace the rest while some but not all songs are pinned), and Add a song. A refinement of a list has no draw to edit, so it shows none of the three. An empty result offers up to three chips that each loosen one filter. Asking again replaces the card: the older one shrinks to a "Replaced" line. Play says "Playing now" only when the player is actually playing; a browser that blocks autoplay reads "Loaded, not playing yet". The filter chips, the pet's lines and failure wording are in `bot-replies.ts`; the server alone decides which songs fit.

Use as reference selects the song meant by "remove that artist". Follow-ups can refine the proposal, search the upcoming queue or return to the whole library. The Look in control (Whole library, This selection, Up next) shows where the last answer looked; picking one sends `scope` with the next request, which wins over the model's reading of the words for that one request, then the control shows what was used again. This selection needs a result and Up next needs songs after the current one. "Add another song" retains matching proposal songs and searches for an additional match without repeating them. Explicit artist, decade and other filter changes replace those filters; unchanged filters carry forward. Artist exclusions accumulate. "Allow Harbor again" withdraws that artist's exclusion while keeping the others; "allow songs played today" withdraws the recent-play exclusion. A scope switch alone cannot lift exclusions. Clear chat starts a fresh selection. The last eight chat messages and the proposal stay in this tab's session storage. The server remembers the songs from the last three library answers the chat showed, for every device you use with this Musimo, and keeps them across restarts. Clear chat does not forget them. Chat settings has Forget shown songs, which clears them on every device and leaves play history, likes and playlists alone. Refinements, questions and cancelled answers are not recorded. Asking again ("another set", "something else") prefers other songs that fit as well. It repeats one when nothing else fits, or, for a most-played request (and, once analysis is on, a "more like this" request), ahead of matches that fit less, and it says so ("1 song repeats from an earlier answer"). The memory is suggestion memory, not a taste score: it does not change play counts, and plays and skips never become a like or a dislike. After navigation or reload, send another request to refresh the queue check before applying a restored proposal.

#### Preview and confirm

Every search answer with songs is stored on the server as a proposal, and the card shows that stored revision, not the chat's own copy of the list. The first answer makes revision 1. A follow-up that arrives while a card is open becomes the next revision of the same proposal (the card says "REVISION 2"). A request to add songs is an `add` edit of the open revision when its filters are the same, so the server picks the songs; with changed filters, or nothing open, the chat's own list is stored as a new proposal, since an edit cannot change a filter. A follow-up carries the songs a person removed, and carries the pinned songs only when it is a library search: one that refines a proposal or the queue drops the pins. A restored card from before this existed has no revision either, so the first Save or queue press only makes the preview, says so, and waits for a second press.

The card's Total is the length stored with the revision, which is what a commit approves. The songs are added up again each time the overview is made, and if that no longer matches (a song changed length) the "In these songs" line says "Length now 2 h 35 min, approved at 2 h 40 min" instead of leaving two totals to disagree. A song the library no longer has is left out of the list and named in a warning that offers Refresh preview first, because confirming would be refused as out of date; if every song has gone the card says so rather than showing an empty list.

Under the summary the card has two lines taken from the songs themselves. "In these songs" is the length, number of artists, the three most common genres, and the year range. "Not known" lists what could not be read, such as songs with no length or year. Tempo and loudness appear only when a measurement recipe is on, only for songs with a fresh measurement, and always with how many songs they cover. A genre name never stands in for them.

Play, Play next, Add to queue, Replace upcoming and Save as playlist send a commit with the proposal id, the revision and a fresh operation id. They never search again. For a queue action the browser waits for the server's receipt and then hands the receipt's ids to `PlayerProvider`. A press while one is in flight does nothing, and the card's buttons wait for the answer.

- If the server says `proposal_stale`, the card says what changed ("First Light: the file is unavailable"), that nothing was saved or queued and that no song was swapped, and offers Refresh preview. Refresh runs the same request again as the next revision, keeping its filters and seed, then says how many songs left and came in. It confirms nothing.
- If the server recorded a queue confirmation but the browser then cannot apply it, the card says so instead of leaving the user to guess: "The server recorded this confirmation, but your queue was not changed", followed by the reason (the queue moved, it is full). A receipt that names a song the card does not hold leaves the queue alone and offers Refresh preview. A second press after that is sent as a repeat, since the first is on record.
- Remove from this list, the pins, Another set and Add a song wait while a chat request, an edit, a refresh or a confirmation is running, and while a stale or unsettled problem is on the card, so none of them can supersede another. An edit can be cancelled like a request.
- An edit makes its own operation id for each press and asks once more with the same id when no answer arrives; if that also fails the card offers Check again, which sends that same id, and the composer, the chips and the card's actions wait until it is settled. If the server says the revision is not the latest or the proposal is gone, the card says "This preview changed" and offers Refresh preview, for a chat follow-up as much as for an edit. Nothing is edited and no new proposal is made until that is pressed; Refresh preview then reads the latest revision.
- Refresh preview leaves out a kept song that has left the library and says how many it dropped. On a refined list (only the rock ones of an earlier answer) the card cannot send a shorter list, so the server leaves the gone songs out and the card says how many. A chat follow-up or a Remove on such a list says the same. A kept song whose file cannot play is named on the card and stays; the rest of the card waits, and Remove on that song stays enabled.
- If no answer arrives (the network drops, the request times out, the server fails, or a success reply cannot be read), the browser asks once more with the same operation id. If that also fails, the card says it cannot tell whether it went through, hides the other actions and offers Check again, which sends the same id again. A retry returns the first receipt, so the playlist is saved once and the songs are added once.
- A second confirmation of the same revision to the same place (Add to queue again after Undo) is sent as a repeat under a new id. After a reload the browser does not remember, so the server answers `already_committed` and the card asks "Do it again?".

#### Undo

Undo restores only the latest bot queue edit, and refuses after the queue or the loaded track changes. Pausing, or pressing play on the song already loaded, does not refuse it. The card shows that refusal ("Can’t undo." with View queue) as soon as the player stops offering Undo, rather than after a press that cannot work. It also restores a large-library shuffle's seed, cursor, total and queue fingerprint, so playback can fetch beyond the loaded window. An edit to upcoming songs leaves the playing element untouched. Undoing Play restores the earlier song paused at its saved position; undoing a first selection restores an empty queue.

#### On a phone

Under the phone breakpoint both layouts draw the same chat page (`PhoneBotPage` in `bot-page.tsx`), laid out like a messaging app:

```text
top bar                              keyboard up
< (pet) Octive         [gear] [bin]  < (pet) Octive         [gear] [bin]
[Whole library][This sel.][Up next]  [Whole library][This sel.][Up next]
messages, newest at the foot         messages, newest kept in view
[Ask Octive for music        ] [>]   [Ask Octive for music        ] [>]
mini player / tab bar                ==== on-screen keyboard ====
```

- One header row: Back, the pet, the name and status, Chat settings and Clear chat. The model is picked in Chat settings; the status line names it. Look in fills the next row with three 44px buttons and keeps its label for screen readers only.
- The page is fixed between the top bar and the player, so it never scrolls the text box away. The conversation scrolls inside it.
- The result card is a message in the conversation, as in the pet's sheet, in both layouts. The Listening room's Draft panel is for wider windows only. The card reaches out under the reply's pet face, and a song's length sits beside its artist, so the title has the row.
- No starter chips under a conversation (the empty chat offers them) and no footnote, except while the chat is locked or the text nears its 2,000 characters.
- The pet does not perch on the mini player on this page; it is in the header.
- The on-screen keyboard: `useKeyboard` (`src/lib/use-keyboard.ts`) reads `window.visualViewport` while the page or the pet's sheet is open, and sets `data-keyboard`, `--keyboard-inset` and `--keyboard-top` on `<html>` while a keyboard is up. The page and the sheet keep below the notch while the top bar is hidden. The log keeps its newest message in view when its box shrinks, unless it had been scrolled up.

Four characters (cat, bird, robot, blob) drawn from boxes and clip paths in `frontend/src/features/music-bot/pet-shape.tsx`, so one drawing scales from 16px to 72px. Where it sits (`pet-host.tsx`, geometry in `pet-placement.ts`):

- **Phone:** 30px inside a 44px button, 7px above the mini player so it stays off the seek strip, with a soft shadow where it perches. On a phone it perches on the floating mini player as it does on Classic's. Hidden, or on a phone with nothing playing, its face takes the Octive tab's icon.

What it does (`pet-mood.ts`, from real events only; it never claims to hear the music): thinking while a request is out; busy during a library scan (`GET /api/library`); offline when the model server does not answer or no model is chosen; then for six seconds after a reply, talking, happy (songs played or queued, a direct command), confused (a question) or apologetic (a failure); talking while an unseen reply waits; a 1.5 second perk-up on a track change; sleeping while the sleep timer runs or after three minutes paused; listening while music plays; otherwise idle.

A reply that lands with the chat closed puts a dot on the pet and "New reply" in its label, and in Normal or Chatty a short bubble for eight seconds. Chatty also says the new track's title, album and number on a track change. Facts only; it never rates a song.

The pet is a button labelled "Octive, music bot. Open chat" (with "New reply." when one waits). Enter or Space opens the chat and focus moves to its text box, or to a question's first quick reply, or to the first control when the box is locked. Escape closes it from inside the chat or from the pet, and focus goes back to the pet. The conversation is a polite live log, and the header's status line says Ready, Thinking or the problem. Right-click, a long-press, Shift+F10 or the context menu key opens the quick menu: Open chat, Clear chat, Size, Sit on, Chattiness, Still pet, Hide and Pet settings.

Settings › Yours › Music bot pet sets the character, name (up to 20 characters), colour (the theme accent, or a built-in family's accent in the half that matches the theme's scheme, kept only where its face stays at AA), size (small, medium, large; phones keep to small or medium), position, chattiness, animation and sounds, and can hide the pet, with a live preview and buttons to see it react. They apply at once and live in this browser in `musimo.pet` (`pet-settings.ts`): a zod schema with a version, each field falling back on its own, and a change that still holds for the page when storage refuses it. Animation follows the device by default, Reduced keeping blinks and fades and dropping hops, sways and travel; the app's global reduced-motion rule still holds every animation still when the device asks. Loops are CSS keyframes in `style.css`, so they cost nothing on the main thread while music plays. Sounds are off by default: a soft two-note chirp for a reply that lands while nothing plays, never over the music and never touching its volume.

Queue persistence holds one active save and one latest pending snapshot. Each HTTP request has an eight-second deadline; intermediate pending edits are replaced by the latest state. SQLite checks the browser's writer epoch and increasing sequence inside the queue transaction, so an abandoned request cannot overwrite a newer edit or Undo. Failures appear in the player. If another browser takes ownership, this browser stops saving and asks for a refresh rather than overwriting that browser's queue. Playback remains local to each browser. Failed saves are not retried indefinitely; subsequent player saves can recover from a transport failure, while an ownership conflict requires refresh.

A question from the bot (clarify) and a refusal it cannot do (mood, energy, tempo and the like need audio analysis, which is not enabled) can come with up to three quick replies the server suggests; tapping one sends it. Failures are said in the pet's voice above the server's or the player's own words, so the 500-song limit reads the same as in the player: a moved queue offers Send again, a full queue offers Replace upcoming instead, and an unusable model answer offers Try again. A library scan, an unreachable model server or no chosen model lock the chat with a page that says why and offers the way out (the scan's progress and a link to Diagnostics, Retry connection, or a model picker). The chat's gear opens its settings: the installed models, Test connection, the rules it reads the library by, Clear chat and a link to the pet's settings.

Direct Pause, Resume and Skip commands use the live browser player. A cancelled, superseded or disconnected request never applies a player command. Browser autoplay failures keep the player's retry message; loading a selection does not claim audio started. See [the review handoff](music-bot-review.md) for mocked versus live verification.

The queue can be changed while it plays. The player context offers `playNext(tracks)`, `addToQueue(tracks)`, `removeFromQueue(index)`, `moveInQueue(from, to)` and `clearQueue()`, and every one saves through `PUT /api/player/queue`, the same call the autosave uses. A save that fails says so in the player's status line, since the queue on screen would then differ from the one that restores after a refresh.

Where the actions are:

- **Song rows** on the Tracks list, album pages, playlist pages and an artist's All songs view have a "More actions" menu with Play next and Add to queue.
- **Albums and playlists** have the same menu for the whole collection: on the album and playlist page headers, on list rows, on playlist cards, and on album cards (over the artwork, shown on hover or focus). A card has not loaded its songs, so the menu reads them first.
- **Up next** has, on each row, a drag handle, move up and move down buttons, and a remove button. The playing track is not in Up next and cannot be removed there; skip it instead. Its header has Clear queue, which keeps the playing track, and Save as playlist, which asks for a name and creates a playlist of the whole queue through `POST /api/library/playlists` in one call.

Play next puts songs straight after the playing track, but behind any songs already queued that way, so two Play nexts play in the order they were chosen. Add to queue puts them at the end. With nothing loaded, either one starts playing the songs instead.

Reordering has three routes to the same move. Drag a row by its handle (native pointer events, so touch works, and dragging near the panel's edge scrolls it; Esc cancels). Or use the move buttons. Or press Alt with Up or Down on a row's title button. The result is announced in a polite live region ("Moved Delta to position 2 of 3."), and so are removal, clearing and saving as a playlist. Focus follows the row that moved, and moves to a neighbour when a row is removed.

Shuffle picks the next song at random, so there is no fixed order to edit. Songs you queue by hand are the exception: with shuffle on, the nearest of them after the playing song plays next, in the order Up next shows them, and chance takes over once they are used up. Removing, moving and clearing all act on the queue as it is shown.

Songs queued by hand survive a reload. the library's saved queue holds ids only, so the player keeps their positions in `localStorage` under `musimo.queue-chosen`, one copy for each name, beside a hash of the queue's ids in order (`queueHash`). It writes them whenever the queue or the set changes, including when one of them starts playing and stops being "chosen". On restore the positions are read back only if the restored queue hashes the same; a queue that differs (another device changed it, or a save failed) drops them rather than putting the wrong songs first. Browser storage is optional: every read and write is wrapped, and without it a reload simply forgets which songs were chosen.

An edit does not take the collection away. The player keeps the source it began with (`album:…`, `playlist:…` and so on) and tracks separately, as `edited`, that the queue has been changed by hand. Up next says "Playing from album Clear Water, edited", and that collection's play button keeps showing Pause while its own song is the one playing. The source follows the playing track (`queueSource`): while it is a song you added with Play next or Add to queue, the queue counts as `queue` ("Playing from your queue") and the collection's button offers Play again; when a song of the collection plays, it is the collection again. A song row on the collection's page is not marked as the playing one once the queue has been edited, because the queue's places no longer line up with the list.

Three cases use a source of their own instead. Clear queue leaves one song and no collection, so the source becomes `queue`. Play next or Add to queue with nothing loaded starts a queue from those songs, also `queue`. A History row starts its queue with the source `history`. A queue restored after a reload has no known collection (`restored`, so no "Playing from" line), and the first edit to it makes it `queue`.

The queue holds at most 500 songs. An addition that would take the queue past that is refused whole, with a message in the player's status line ("The queue is full. It holds 500 songs and this would make 502. Nothing was added."), and nothing is saved. `PUT /api/player/queue` refuses more than 500 ids as well, so the limit holds even for a client that skips the check. Save as playlist uses the queue's own size, which is within the 500 songs a playlist create accepts.

Starting playback keeps the collection in place. Loading feedback appears in the Library header's readiness tag on the list views (detail pages have no such header, so their own buttons disable while a collection loads), and other cards keep their play buttons hidden until hovered or focused. Touch layouts keep the buttons visible.

## Deezer account

A signed-in Deezer account can play a catalog song without saving it into the library. Now Playing names the source: Deezer account, Library, or Preview. A Spotify preview stays Preview (or Spotify preview). It is not account audio.

Play fetches the whole song, writes `job.json` beside that file with the track id, then runs the account-file command. The command reads the id from that file. A download already writes it. Without it the command fails and Play falls back to the preview. The row says Fetching… until the file is ready, and pressing it cancels the wait. Seek works after that. The browser plays `/api/player/account/dz-{id}/file`. The cookie stays on the server. The listening file is cached for the session under the data directory, apart from downloads, and removed when the cookie is removed or replaced. Removing or replacing the cookie mid-stream stops the account stream. Diagnostics carries a `mark` for that file, not the cookie, and the player stops when the mark changes.

A download and a Play share one cookie. Play holds it only while it fetches; the file command runs after the cookie is free, so a download is not stuck behind that command. If the account is already busy, Play says "The Deezer account is busy." and leaves the other one running. The cookie, the listen cache and that lock belong to the house, so one name being busy stops every name.

The song can join the Musimo queue (Play next, Add to queue, Play from here) and a Musimo playlist, mixed with library songs. A library song plays from disk. A Deezer song plays through the account. The liked playlist is Musimo's. History may list an account listen as Played from Deezer. The library play count does not move.

The sign-in is cached and reused from Diagnostics as `deezer_listen`. A row does not sign in on its own.

## Gapless playback

The library has two `<audio>` elements in the footer, `audio.library-audio`, that swap roles. One plays (`data-role="active"`) while the other holds the next track (`data-role="standby"`). The previews' element is separate and never involved.

The next track starts loading when the playing one has `PRELOAD_LEAD_SECONDS` (15) left, or straight away for a track shorter than that. It is loaded into the standby element from `/api/player/stream/{id}`, and the choice is kept: shuffle picks at random, so the song that was loaded has to be the song that plays. Repeat one loads the same track again, so a looped track is gapless too, and repeat all loads the first track from the last. Anything that could change what is next drops the loaded track and loads the new one on the next timeupdate: a queue edit, and switching shuffle or repeat. Playing a preview drops it too. On a metered connection (`navigator.connection.saveData`) the standby element gets `preload="metadata"` and nothing beyond it, so the track starts the way it did before this existed.

The handover happens inside `loadLibrary`, which every route to a new track goes through: the end of a track, Next, and picking a row of the queue. It hands over only when the track asked for is the one the standby element holds, and only for a track that starts at once from the beginning, so a restored queue and a scrub are loaded as before. Where the stream's length agrees with the library's (within 2 seconds), a timer starts the standby element 40 ms before the end, since the `ended` event arrives late and a live album or a mix would carry the gap into the music. Otherwise the `ended` event does the same handover. If the standby element could not load its track, or the browser refuses to start it from a script (iOS does until an element has been started by a tap), the track is loaded into the playing element the ordinary way, and the second case stops preloading for the rest of the session.

The timer is kept by a Web Worker, not by `setTimeout` on the page. A hidden tab, which is where most listening happens, holds page timers to about one a second, so a page timer for a wait of 400 ms fires up to a second late and `ended` takes over with a small gap; a worker's timers are not held to that while audio plays. The rule and the arithmetic are in `frontend/src/features/player/handover.ts` (`handoverDelay`, `lengthsAgree`), the worker is `handover-worker.ts` and the page's side of it is `handover-clock.ts`. The clock is made on first use and the worker is started when the standby element begins loading, well before the last second, so it is ready when the wait is armed; the first `arm` never pays for loading it. Nothing about it is on the main bundle's critical path, since Vite builds the worker as a file of its own, fetched from the same origin the CSP already allows.

The wait is worked out from the playing element's `currentTime` and `duration`: real time to the end is what is left divided by `playbackRate`, less the 40 ms lead. It is armed only inside the last second and only while the element is playing, and it is worked out again on every timeupdate and on seek, play and rate change, each of which replaces the wait before it. A pause, a load of any other track and a discarded preload cancel it. Every wait carries a token, and the worker's answer for a token that is no longer current is ignored, so a wait made for one track can never start the next one. When the worker answers, the player checks again that the track and element are the ones the wait was made for, that the element is not paused and that it is still inside the last second. Where workers are unavailable, or one fails to start, the same wait is kept with `setTimeout`, which is right in a visible tab and late in a hidden one, and `ended` remains the safety net in every case.

What follows the song rather than the element, and is set at the handover: the queue index and the saved queue position, the scrobble (the submission for the track that ended, then now playing for the new one), the play history, the Media Session metadata and position state, the seek bar and length, and the visualizer feed (see [the visualizer note](visualizer.md#the-two-library-elements)). Only the element in play is listened to: the standby element's load, length and errors change nothing on screen until it takes over. Previous restarts the track after 4 seconds of playback and goes to the previous track before that, as before.

The suite checks the mechanism (what loads where, what takes over, what is reported) but cannot hear the join: headless browsers have no audio output to listen to. Check it by ear on a live album or a mix, in the browsers you use, when this code changes.

## Crossfade

Off by default. Set under Your settings, [Playback](settings.md#playback), from 1 to 12 seconds (`musimo.crossfade`), it overlaps the tail of one library track with the head of the next, using the same two elements as gapless playback. It reads `frontend/src/features/player/crossfade.ts` for the rule, `frontend/src/features/player/fades.ts` for the curves and `frontend/src/features/player/crossfade-settings.ts` for the stored value.

It starts from `maybeCrossfade` on the playing element's timeupdate, once all of this holds: the standby element has loaded the next track far enough to play (`readyState` of `HAVE_FUTURE_DATA` or more, so a metered connection, which loads metadata only, never crossfades), no sleep timer ends after this track, and `crossfadeSpan` says the join is due. `crossfadeSpan` returns 0, leaving it to gapless playback, for repeat one and for consecutive tracks of one album (the next song is queued straight after the playing one and shares its album). The wrap from an album's last track to its first under repeat all, and the same album queued out of order, do crossfade. The overlap is the setting, capped at half of either track, and once it is due it is never longer than what is left of the playing track, so a late start still ends when the track does. If the next track is not ready in time the ordinary handover does the join.

At the start of the overlap the new track takes over everywhere at once, by the same route as any handover (`finishTrack`, then `loadLibrary`): the queue index and saved queue position, the scrobble (the submission for the track that is ending, then now playing for the new one), the Media Session metadata and position state, the seek bar and the visualizer feed. The old track is not paused. Its element keeps playing as `fadingOut`, still marked standby, and is not touched by preloading until it is done. Every 100 ms the two levels are set on top of the volume and ReplayGain, on equal-power curves (`fadeOutGain` and `fadeInGain`), so the join holds one loudness. When the old track's element is out of sound it is paused. Its own events (pause, ended, timeupdate) are ignored like any standby element's.

Anything else that loads a track ends the overlap: Next, Previous when it goes back a track, a row of the queue, a preview or Close. Pausing during it cuts the old track and pauses the new one, rather than freezing two. If the browser refuses to start the standby element from a script, the old track is cut for the new one as in gapless playback.

Like gapless playback, the suite checks the mechanism but cannot hear the join. Check it by ear when this code changes.

## Sleep timer

The Now Playing control row has a Sleep timer button, a moon icon that opens a menu (`frontend/src/features/now-playing/sleep-timer-control.tsx`): Off, End of track, End of album or queue, and 15, 30, 45 or 60 minutes. The running choice is checked. While one runs, the moon is accented and the time left shows beside it, in tabular figures, with a button to cancel it (choosing Off does the same). It is an icon, not a select, so the control row stays on one line at laptop widths. The menu opens upward and works like the row menus: Enter or Space on the button opens it on the running choice, the arrow keys, Home and End move, Escape closes it and returns to the button, and a click elsewhere closes it. A timer is not saved: a reload clears it, and so does closing the player.

- **End of track** stops after the track that is playing. Skipping to another track moves it to that track.
- **End of album or queue** stops after the last track in the queue, which for an album is the end of the album. What is queued is followed as it is edited. Shuffle and repeat never reach a last track, so the menu item is disabled while either is on (it says "Not with shuffle or repeat"), and turning one on cancels a timer that was set ("Sleep timer cancelled. Shuffle and repeat never reach the end of the queue."). Its time left is the rest of the track plus the songs still to come.
- **Minutes** counts real time, so pausing does not stop it. A preview leaves it running; a preview does clear the two end timers, which have no end to wait for.

The last five seconds are a fade to silence (`SLEEP_FADE_SECONDS`, `rampDown`) applied on top of the volume and ReplayGain, then playback pauses and the level goes back to normal. For the end timers the fade is the last five seconds of the final track. `finishTrack` reports the listen as for any finished track (scrobble submission and history), pauses, and loads the track that would have come next without playing it, so pressing play carries on from there and the saved queue points at it. With nothing next, the last track stays loaded and paused. For a minutes timer the pause can come in the middle of a track or a crossfade, and both elements are paused. The pause goes through the ordinary pause event, so the saved queue position and the Media Session state are updated as for any pause. The status line says "Sleep timer ended. Playback paused." No crossfade starts out of a track that a sleep timer ends after.

The player context exposes `sleep` (the choice and the seconds left, or null) and `setSleep(choice | null)`. The types and the menu's values are in `frontend/src/features/player/sleep-timer.ts`.

## Tracks that cannot be played

When a library track errors, the player skips to the next one and says which in its status line: "Skipped Delta, it could not be played". The next track follows the same rules as Next, so shuffle and repeat all apply. After `MAX_FAILURES` (3) tracks fail in a row the player stops and says so ("Stopped after 3 tracks in a row could not be played. Check that the music folder is mounted."), because that many in a row more likely means the music folder cannot be read than that every song is broken. A track that starts playing clears the count, as does starting a new queue. A queue restored on page load that starts on a broken track skips past it without starting playback. A track that only failed to preload is not skipped for that: it is loaded the ordinary way when its turn comes, and skipped then if it still fails. Repeat one does not retry a broken track, since that would never end.

## Play history

Each library track that actually played is recorded in a history kept in this browser for the current name, under `musimo.play-history.<id>` (`frontend/src/features/player/play-history.ts`). A track counts once it has played past 10 seconds, or to its end when it is shorter than that. Catalog previews are never recorded, and neither is a saved queue that only restored its position: the element has to be playing. The list is newest first and capped at 200. A track is not recorded again while it is the most recent entry, so repeat one and replaying the same song add one row. Each entry keeps only what a row and a replay need: id, title, artist, album, duration, the cover and artist and album ids, its ReplayGain tags (so a replayed song is levelled) and when it played. Storage that is missing, blocked or unreadable is treated as an empty history, and a failed write is ignored.

The History tab on Now Playing lists the entries with the time relative to now ("5 minutes ago", "yesterday"), refreshed each minute while the tab is showing. A row plays that track again. With a queue loaded it slots in straight after the playing song and plays, so looking back does not throw away what was lined up; with nothing loaded it becomes a queue of one whose source is `history` ("Playing from your history"). A row has the same More actions menu as other song rows, with Play next and Add to queue. Clear history asks in the tab, not in a browser dialog: the button is replaced by "Clear 23 tracks?" with Clear and Keep buttons, and focus starts on Keep so a stray Enter clears nothing. Escape or Keep puts it back and returns focus to Clear history; Clear empties the list and the stored copy, and focus moves to the tab's toolbar since the button is disabled with nothing to clear. A polite status line announces the question and the outcome, and the question goes away if the history empties or the tab is hidden. `e2e/history.spec.ts` covers it. The player context exposes `history` and `clearHistory()`.

## About this track

The About tab on Now Playing says what the library holds for the playing track, since the reason to self-host is owning the files. It draws nothing for what the library does not send: a row with no value, and a section with no rows, are left out, and a zero for bit depth, bitrate, sample rate, size, year or a track number counts as "not known". Its details are a bonus, so a failed read shows less and never an error. Facts are a two-column list: the label in the small text size, muted, and the value in the body size, so the values are what the eye lands on. The label column is as wide as the longest label and the values take the rest, at the panel's 500px and on a phone alike; long values, the path included, wrap.

- **File**: format (the file's extension, or the content type's subtype), bitrate, sample rate, bit depth, channels (Mono, Stereo, or a count), size and the path as the library reports it, relative to the library.
- **Release**: album, year, label, genre, track and disc number, and contributors grouped by role ("Producer", "Performer (bass)"). The song's own tags win over the trimmed copy the queue carries. The label is the album's `recordLabels`.
- **Listening**: play count (when above 0) and last played, from the library's `playCount` and `played`. Last played is relative to now, with the full date in its tooltip.
- **More you own**: up to 8 other albums by the track's artist, newest first, each linking to its Library page, and the rest of the playing album (up to 10 songs, then "and N more"). "Open album" beside the second goes to `/library/albums/{id}?track={song}`, and the album page marks that song as playing (`aria-current`, the playing row's background) and scrolls it into view, even when the queue was not started from that album. The `track` search parameter is read as text, because the router turns a value of only digits into a number.
- **Look for a better version**: for a lossy file (mp3, aac, m4a, ogg, oga, opus or wma) with a bitrate known and under 192 kbps (`LOW_BITRATE_KBPS`), a quiet link to Search for "artist title". A lossless file, or one with no known bitrate, never gets it. M4A counts as lossy because it is nearly always AAC; an ALAC file in one has a bitrate far above the threshold.

The song comes from `GET /api/player/song/{id}`, which passes the library's whole song through, so no field list has to grow. The trimmed track fields (`TRACK_FIELDS`) stay as they were, since they are kept for every song in the library. The format chips under the artist read the same query (`['player-song', id]`), so opening the tab costs no second request. The album and artist reads use the query keys the Library pages use, and wait until the tab is showing. The rules and wording are in `frontend/src/features/now-playing/track-info.ts` and the tab in `frontend/src/features/now-playing/about-track.tsx`.

## Waveform seek bar

The seek bar on the Now Playing page draws the track's peaks in place of a line: one centred bar to each 4 pixels of the bar's measured width, the played part in the accent, the rest in the strong line token (`fill-accent`, `fill-line-strong`), and a 2 px playhead in the accent. In the Listening room, whose card is tinted by the cover, the played part and the playhead are the text token and the rest the text token at 22% (`fill-text`, `fill-text/22`); the `tone` prop picks which, and the box is 36px tall in Classic and 40px in the room. Every colour is a theme token, so a theme repaints it with no drawing code. The footer player, the phone mini player and the full screen and popout controls keep the plain range.

The range input is still the whole control. The peaks are drawn behind it and the input is made invisible over them, so the keyboard (arrows step 0.1 seconds, and the page's own keys leave a focused slider alone), the pointer (click and drag), the disabled state and the accessible slider (`Playback position`, with its value and maximum) are the browser's own and unchanged. The one thing the box takes over is the focus ring, which an invisible input cannot draw. The thumb is given no width so the input's travel is the whole box and a click lands where the playhead is drawn. It is the same element with or without peaks, so a focus in progress survives them arriving, and the box is 32 px tall either way so the controls under it do not move.

While the peaks load, and whenever there are none (a 404 or 503, a network error, a body with fewer than two peaks), the bar is the plain range and nothing on the page says anything went wrong. The component and its query (`['player-waveform', id]`, kept while cached, no retry) are `frontend/src/features/now-playing/waveform-seek.tsx`. The arithmetic (how many bars fit, folding the peaks to that many by the loudest in each, the SVG path) is `frontend/src/features/now-playing/waveform.ts`.

### Where the peaks come from

`GET /api/player/waveform/{id}` (`backend/api/waveform_api.py`, worked out in `backend/library/waveform.py`) returns `{"peaks": [...]}`: 800 values from 0 to 1, the loudest in the track being 1. A peak is the loudest sample in a 12.5 ms window of the first audio stream, decoded by ffmpeg to 8 kHz mono, and the windows are folded to 800 points by their loudest, so the result does not depend on the length the library reports. A track under 800 windows repeats them. Values are stored as one byte each and sent to three decimals.

- **Source.** The song row holds the file path. If that path resolves to a regular file inside an enabled library root (`MUSIMO_LIBRARY_ROOTS`, after `..` and links are resolved, so a path cannot leave the root) and it is not a symlink, ffmpeg reads the file there. Anything else has no peaks. ffmpeg's error output is discarded, since it can carry a path.
- **Cache.** The SQLite `waveforms` table holds one row per song: the id, a fingerprint and the peaks. The fingerprint is the algorithm version plus the file's size and modified time in nanoseconds. A request whose fingerprint differs from the row's is decoded again and replaces the row, so a replaced file is picked up and rows do not pile up. A hit costs one song lookup, one `stat` and one read.
- **Queue.** One decode runs at a time and up to 8 requests wait behind it (`QUEUE_LIMIT`), so a big album does not start twenty ffmpeg processes. A ninth is refused with 503 and `Retry-After`. A request that waits longer than 30 seconds (`QUEUE_WAIT_SECONDS`) gives up with 404. Once it has its turn a request checks the cache again, so two requests for one track decode it once.
- **Timeout.** A decode is stopped after 60 seconds (`DECODE_SECONDS`): ffmpeg is killed and the request is 404, never left hanging. A file ffmpeg cannot decode and a missing ffmpeg are 404 too. Those failures are remembered in memory (256 tracks, until a restart or until the file changes), so a broken file is not decoded again on every visit.
- The item id is checked like every other route's. A missing song is 404.

## Volume levelling

Library tracks are levelled with ReplayGain when the file has the tags. Songs carry an optional `replayGain` object (`trackGain` and `albumGain` in dB, `trackPeak` and `albumPeak` as a fraction of full scale). The backend keeps it on the song row and passes it through on album, playlist, queue and artist responses, and the browser reads it as an optional `replayGain` on `libraryTrackSchema`. A file with no tags has no `replayGain` and plays unchanged.

The maths is in `frontend/src/features/player/replay-gain.ts` and has no player state in it. `replayGainMultiplier` turns a track's tags, the mode and the pre-amp into a factor: Off gives 1, Track uses `trackGain`, and Album uses `albumGain` while the track is `playsAlbumInOrder` (shuffle is off and the song before or after it in the queue is from the same album), else `trackGain`. Album mode also falls back to `trackGain` when a file has no `albumGain`. The pre-amp is added to a track that has a gain; a track with no usable gain is never touched. The factor is capped at 1 / peak, using the peak that matches the gain in use, so the loudest sample cannot pass full scale.

The player applies the factor to each audio element's `volume` (`outputLevel` and `applyVolume` in `frontend/src/features/player/player.tsx`), on top of the volume the person set. The `volume` state, the slider and `musimo.player-volume` are never changed by levelling, so the slider reads what they set. The standby element is levelled for the track it has preloaded, so a gapless handover arrives at the right volume, and an element finishing its last moments is not touched. It is re-applied when the setting, shuffle, the queue or the playing track change. Previews are not levelled.

An audio element's volume tops out at 1, so a gain above 1 (a quiet track with a positive tag or pre-amp) cannot be reached through `volume`. Cuts always work. The boost goes through the audio graph instead:

- **Both library elements get the boost.** `routeToAnalyser` makes each library element's source and connects it through a gain node of its own to the bus the visualizer listens on (see [the visualizer note](visualizer.md#the-audio-graph)). `splitLevel` in `replay-gain.ts` is a pure helper that splits the level (slider x fade x factor) into an element `volume` and a node `gain`: the element keeps everything up to 1 and the node carries only the part above it, so 0.4 x 1.5 is volume 0.6 and gain 1, and 1 x 2 is volume 1 and gain 2. A gapless or crossfaded run is levelled the same on every track.
- **The peak cap always holds.** The factor is already held to 1 / peak, and the boost is used only when the tag that levels the track carries a usable peak (`replayGainHasPeak`), since without one nothing says a boost fits under full scale. A track with no peak is capped at 1.
- **Previews are never boosted.** They stay on the preview element and never touch Web Audio.
- **No graph, no boost.** Until a library track has played, and whenever the context is not running, no node exists or is used, the gain is 1 and the volume is worked out exactly as before. The level is applied again once `routeToAnalyser` finishes, so the node exists by then.

The mode and pre-amp are per-browser settings; see [Playback](settings.md#playback). Musimo does not write ReplayGain tags when it downloads yet, so only files tagged elsewhere are levelled.

## API

- `GET /api/player/capabilities`: whether a music folder is configured and readable, and Musimo's version.
- `GET /api/library/albums`: whole-library album browsing. `q` (album or artist name), `sort` (newest, title, artist or year), repeated `genre` and `year`, `offset` and `size` are applied on the server, which returns the page, the matching `total` and the `genres`/`years` present across the library. Albums are grouped from the indexed songs.
- `GET /api/library/artists`: whole-library artist browsing. `q`, `sort` (name, albums or recent), repeated `genre` and `year`, `show` (favourites, played or unplayed), `offset` and `size` are applied on the server, which returns the page, the matching `total` and the `genres`/`years` present across the library. Each artist is described from the indexed albums: an artist matches a genre or year if any of their albums carries it; recent is their newest album's added date; played means any of their albums has a play. Favourites are rows in `artist_favourites`.
- `PUT` and `DELETE /api/library/artists/{id}/favourite`: star and unstar an artist.
- `GET /api/library/tracks`: whole-library track browsing. `q`, `sort`, repeated `genre` and `year`, `offset` and `size` are applied on the server, which returns the page, the matching `total` and the `genres`/`years` present across the library. The list is the indexed songs. Building it reads the index, including the cover rows the scan stored in `library_covers`, and does not walk the music folders. The server builds that view in the background after it starts, and again after the index changes, including the track title sort and the newest-album sort, so the first page does not wait on it. A change to a song or a cover drops the cached view. Supported sorts are title, artist, album, year, duration and newest.
- `GET /api/library/tracks/search`: matches from the index, for the playlist song picker.
- `GET /api/library/tracks/selection`: the same filters without paging, for Play all and Shuffle. `shuffle=true` shuffles the whole filtered library, including songs past the 50,000 song browse cap, and returns the first `limit` songs (at most 500, the saved queue). When more songs remain it also returns a `seed` and a `cursor`. `POST /api/library/tracks/shuffle` reads the next window from that seed (`cursor`, `limit`, and `skip` for the ids still queued when a pass ends). `POST /api/library/tracks/lookup` turns a batch of ids back into songs.
- `GET /api/player/song/{id}`: song details for a single track, passed through whole. The About tab reads its file facts (`suffix`, `bitRate`, `samplingRate`, `bitDepth`, `channelCount`, `size`, `path`), listening record (`playCount`, `played`), tags and `contributors` from it. `GET /api/library/albums/{id}` passes `recordLabels` through the same way.
- `GET /api/library/playlists`: playlists stored for this install, plus `liked_id` for the linked playlist. Identifying it here is a plain read and never creates one.
- `GET /api/library/playlists/liked`: reads the stored link from SQLite `linked_playlists`, adopts an existing playlist named Liked when none is stored, otherwise creates one, and clears a dead link.
- `GET /api/library/albums/{id}`, `GET /api/library/artists/{id}` and `GET /api/library/playlists/{id}`: detail resources.
- `GET /api/library/artists/{id}/tracks`: all unique tracks from the artist's albums, fetched with bounded concurrency for Play all and Shuffle.
- `POST`, `PATCH` and `DELETE /api/library/playlists`: create, rename and delete playlists. Deleting the linked liked playlist is refused with 409. `POST /api/library/playlists/{id}/songs` adds a song or removes it by its current playlist index.
- `GET /api/player/stream/{id}`: the file. A single byte range is answered; a second range is refused.
- `GET /api/player/art/{id}`: cover artwork from the file or from an image beside it. The image beside a file is the one the scan recorded for that folder (`cover`, `folder`, `front` or `album`; a disc folder uses its parent). A missing cover is 404. An artist uses their newest album cover.
- `GET` and `PUT /api/player/queue`: restore and save the library play queue. `PUT` takes `ids` (at most 500), the `current` id, which must be one of them, and the position in milliseconds. Every queue edit sends one.
- `POST /api/player/scrobble`: report now playing and completed listens.
- `GET /api/player/lyrics/{id}`: the library structured lyrics with an LRCLIB fallback. Each line's `start` is in milliseconds, and an item's `synced` says whether its lines are timed. Now Playing follows timed lines from the player's position, in the Lyrics tab or in the large lyrics view that takes over the content area with the track's transport in a strip along the bottom; see [Lyrics](now-playing-popout.md#lyrics).
- `GET /api/player/waveform/{id}`: about 800 normalized peaks (`{"peaks": [0.12, ...]}`) for the Now Playing seek bar, worked out once with ffmpeg and cached in SQLite until the file changes. 404 when there are none or the wait or decode timed out, 503 with `Retry-After` when the line for the decoder is full. See [Waveform seek bar](#waveform-seek-bar).

## Playback details

Space toggles library playback as well as previews, everywhere but a text field, select, button or link. The Now Playing page adds its own keys, on top of that: left and right arrows seek five seconds, Shift with either goes to the previous or next track, up and down arrows change the volume, M mutes, L opens the lyrics tab (and again, the large lyrics view, which Escape or L closes), Q opens Up next, and `?` opens a cheat sheet dialog listing these and the stage's keys. They are not taken from a text field, select, slider, tab list or menu, or while a dialog such as the command palette is open, and while the stage is full screen or focused its own keys are the ones that act, so nothing is done twice; see [the popout note](now-playing-popout.md#keyboard). The Now Playing stage supports F for full screen, Esc to leave full screen or close the popout, left and right arrow keys to seek by five seconds, up and down arrows to adjust volume, M to mute, N and P to skip tracks, V to switch between artwork and the visualizer, and `[` and `]` to walk the visualizer's presets. N and P are the transport, so the presets take the brackets beside them. The preset select in the stage's preset bar (or the Listening room's pill) chooses the preset, and its arrows step through them.

Library playback is analysed for the visualizer. Every `play` event on a library element calls `routeToAnalyser`, which builds one `AudioContext` the first time (`audio-graph.ts`), resumes it and routes the element through its gain node into the bus butterchurn listens on. Both library elements have to reach that same bus, so the visualizer keeps drawing after a handover; see [the visualizer note](visualizer.md#the-audio-graph). The source is only attached once the context is running, so a suspended context can never silence the track; if the browser suspends it later (a hidden tab, another app taking the output on iOS), the next play or the tab becoming visible again resumes it. Previews are never attached: they stream from provider CDNs without CORS headers, and a media element source on such audio is silenced for good.

Persistence uses browser storage keys `musimo.player-volume`, `musimo.player-shuffle`, `musimo.player-repeat`, `musimo.library-layout`, `musimo.now-playing-view` (artwork or visualizer), `musimo.now-playing-tab` (up-next, lyrics, about or history), `musimo.play-history.<id>` (see [Play history](#play-history), one list per name), `musimo.replay-gain` (off, track or album) and `musimo.replay-gain-preamp` (dB; see [Volume levelling](#volume-levelling)), `musimo.crossfade` (seconds, 0 is off; see [Crossfade](#crossfade)), `musimo.lyrics-offset` (a timing nudge per track, at most 200), `musimo.visualizer-preset` (a MilkDrop preset's name) and `musimo.now-playing-visualizer-notice` (the no-WebGL 2 notice has been shown). The queue autosaves every 10 seconds of playback and on pause or close. Now playing scrobbles on play and submits on track end. Previous restarts the current track after 4 seconds of playback. Repeat one is available. MediaSession handlers provide play, pause, next and previous, and the session's metadata and position state (duration, position, rate) follow the element in play, refreshed on load, play, pause, seek and a length change and at each handover.

Now Playing is for library tracks only. While a catalog preview plays, the page says "A preview is playing." and that Now Playing and its visuals play with tracks from your library; with nothing loaded it says "Nothing playing yet."

Every item id is checked for length and characters before the file is opened. Stream and art answer from that file, after the stored path is checked again. A missing file is 404.

Musimo has no control that deletes a song, album or artist. Remove the file from the music folder. The next scan drops the row, and the playlist entries, play counts and queue rows that used its id go with it.

It cannot judge how the bars look, so look at them on a real track when the drawing changes.

Track browsing reads the indexed songs, so filters, sort and totals describe the library. Each song keeps only the fields the browser reads. Shuffle keeps an id for each further song for the length of the pass. A scan bumps the library revision, so a new download appears in the next read.

Embedded artwork supports ID3, FLAC, MP4 and the base64 picture comments used by Opus and Vorbis. The front cover is preferred; malformed picture comments are ignored so another valid cover can still load. `tests/test_comment_artwork.py` checks real Opus and Vorbis files, cover preference and malformed comments.
