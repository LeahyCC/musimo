# Settings reference

Settings are validated and stored in SQLite. Edit the form, then use Save changes. Successful saves apply without a restart and publish a durable event. They survive container recreation when the data volume remains attached.

The Server page is drawn for the layout in use, from the same rows. Classic has a sticky section index (Your library, Audio quality, Queue & retries, Sources, Music bot) beside bordered section cards. The Listening room has no index: each section is a title and a line on the left and its rows in a card on the right. A row is a label, a line of help, and a field or a `Switch`. A value that a container variable sets shows a "Set by environment" badge (ENV in the Listening room) and cannot be edited. Sources lists what the server reports as download sources, each with a switch.

The sticky save bar appears only when there is something to say: while there are unsaved changes ("You have unsaved changes." with an enabled Save changes button), after a failed save (the error, with the draft kept), and for six seconds after a successful save ("Saved. You can safely refresh."). With nothing changed there is no bar and no idle Save button. The bar carries the `.save-bar` hook that `e2e/phone.spec.ts` measures against the bottom bar.

A status summary at the top of the Settings page shows overall system readiness (ready or needs attention) with a link to Diagnostics for detailed component status. The Diagnostics "Ready to download?" strip reads the same answer, and words it to match the checks beneath: "All systems ready" only when every check passes, and "Ready to download. 4 of 6 checks pass; the rest are notes, not faults." when the system is ready but some checks are only notes (a player that is not set up, a download never attempted). Both call `systemIsReady` in `frontend/src/features/diagnostics/readiness.ts`, so they cannot disagree. The system is ready when every library root is mounted, writable and reporting free space, the library scan is `idle`, `scanning` or `done` (a finished scan is healthy, only a failed, cancelled or interrupted one is not), the library is reachable whenever the server reports it at all, the YouTube helper is healthy, and the last download did not fail. `readiness.test.ts` covers each rule.

## Editable settings

Music bot settings are under Music bot on the Server page:

- `ollama_url`: default `http://127.0.0.1:11434`, reachable from the Musimo server. In Docker, use the host's reachable address, such as `http://host.docker.internal:11434` on Docker Desktop. HTTP and HTTPS are accepted; credentials, paths, queries and redirects are not. Save the address, then Test Ollama connection to list installed models and measure the connection time.
- `ollama_model`: chosen in the chat, from Pick a model when none is set or from the chat's own settings (the gear in its header), and remembered here. No default is selected and no model is downloaded. Missing models and models that fail structured-output validation show an error. Refresh models after installing or removing a model in Ollama.
- `music_timezone`: IANA time-zone name, default `UTC`. Set it to your local zone, for example `Pacific/Honolulu`, before using "played today". Day boundaries include daylight-saving changes where applicable. The `tzdata` package supplies time-zone data on Windows.
- `audio_scalar_recipe`: default empty, up to 80 characters. The id of the tempo and energy recipe whose measured rows the bot may read; the only one in the code is `tempo-energy-v1`, and it is not set until its listening check passes. Empty means audio analysis is off: the bot refuses tempo and energy requests and ignores any rows. Anything but empty or a registered recipe id is rejected.
- `audio_embedding_recipe`: default empty, up to 80 characters. The id of the sound similarity recipe. No recipe is registered for it yet, so only empty is accepted. See [song characteristics](audio-profile-spec.md) for both.

These use the existing SQLite settings table and environment seeding/locking rules. The Ollama settings needed no migration; the two recipe rows are seeded on first start like any new setting, and the measurement tables they point at arrive with schema 9 (see [song characteristics](audio-profile-spec.md)). The model receives bounded chat and tag context, never the full library, audio files or lyrics. Chat history stays in the current browser tab's session storage and can be cleared.

The music bot pet (character, name, colour, size, position, chattiness, animation, sounds, hidden) is not a server setting. It lives in this browser under Settings › Yours › Music bot pet, in `musimo.pet`, like themes; see [the player notes](player.md#the-pet).

- `library_label`: Music by default, 1–60 characters.
- `output_format`: original, m4a, opus or mp3. Default original. M4A/Opus conversion depends on the actual source; the application must not promise lossless transcoding.
- `concurrency`: 1–3, default 2. Parallel download workers. Concurrency can also be changed from the Classic Downloads page's Parallel downloads chip, and the queue sheet's, which honour the lock.
- `max_attempts`: 1–4, default 4. For a song from search, how many times to walk the source list (one is a single pass). For a pasted link or a podcast, how many times to retry that one download. It sits with the source list, next to `tries_per_source`.
- `retry_base_seconds`: 1–30, default 2.
- `retry_cap_seconds`: 30–300, default 60.
- `pace_tracks`: 0–500, default 0. How many tracks may finish before a wait. A failed or cancelled track does not count. 0 turns the pause off.
- `pace_minutes`: 0–1440, default 0. Minutes to wait after those tracks have finished, before the next ones start. 0 turns the pause off. The pause runs only when both numbers are above 0. It is there so a long queue does not keep the connection busy the whole time. The same tracks still download. The wait is kept across a restart, and the Downloads page says when the next tracks will start.

Set `MUSIMO_` plus the uppercase key in the container environment to seed and lock a value on first creation, for example `MUSIMO_CONCURRENCY=3`. An on or off setting takes `1`, `true`, `yes` or `on` for on and anything else for off (`MUSIMO_DEEZER_AUDIO=0`). Later env changes do not replace an existing row. Its original env name remains visible in the UI and API, and PATCH returns 409 for a locked setting. Removing the variable does not unlock the database record. There is no unlock UI yet.

Deployment variables are separate: `MUSIMO_BIND`, `MUSIMO_PORT`, `PUID` and `PGID` control Compose. `MUSIMO_LIBRARY_ROOTS` lists the mounted Linux paths the scanner reads. `MUSIMO_ANALYSIS_TOKEN` is the secret the app shares with the optional audio worker (`docker compose --profile analysis`); empty keeps the worker's lease routes off, and any long random string set for both turns them on. `MUSIMO_WATCH_MODE` is `native` by default; use `poll` for external-change checks on Docker Desktop Windows or network shares. `MUSIMO_POLL_INTERVAL_SECONDS` defaults to 300 (five minutes); lowering it makes external changes appear sooner but uses more CPU. A label does not move or rename a folder. The image fixes application data at `/data`; `MUSIMO_DATA_DIR` is a local-development override, not a supported Compose mount relocation.

## Download settings

- `destination`: a writable root already listed in `MUSIMO_LIBRARY_ROOTS`, default `/music`. Read-only mounts are disabled in the destination selector and rejected by the API.
- `naming_template`: relative path tokens, default `{album_artist}/{album}/{track:02d} - {title}`. A live naming template preview is available at `/api/naming-preview`.
- `source_order`: who a catalog song asks, first to last. Default Deezer account, then YouTube. SoundCloud is added from the list. An empty list is rejected. A row that is paused, turned off, or a Deezer account with no cookie or with account audio off is marked on the row and skipped. A row that is blocked or has just failed is marked too, and still runs until repeated blocks pause it. The source switches under the list show the same problem. The Deezer switch shows the catalog probe. The Deezer account switch shows that account's downloads. The order list still calls the account Deezer. The queue card names the first row that can run as soon as the song is queued. If every row is off, the song fails. If the only hold is a pause, the song waits.
- `tries_per_source`: 1–4, default 1. Download failures on the current source before the next one. A search with no song moves on.
- YouTube cookies: a Netscape `cookies.txt` pasted under Sources. The file is `youtube-cookies.txt` on the data volume, mode `0600` where the filesystem allows it. Settings only learns that a file is saved. The text is not stored in the settings table, not returned to the browser, and not written into the activity log. Clear it with Remove cookie, then Save. An age-restricted YouTube video needs this. Other sites in a full browser export are dropped, and HttpOnly rows (written `#HttpOnly_<domain>`) are kept, since YouTube's sign-in cookies are among them. yt-dlp writes its cookies back to the file it reads when it closes, so each worker reads a private copy beside the saved file, named `youtube-cookies.<process id>.txt`. A running job therefore never undoes a new paste or a removal. The copy goes when the worker exits. A stopped worker cannot remove its own, so the server removes the copy for that process and for the interpreter a Windows launcher started under it. A new paste, Remove cookie and the next start clear any that are still left.
- `file_command`: Command for the account file. Leave empty to keep the file only when it already plays. The file path is added as the last argument. Musimo does not run a shell. Play uses the same command, after writing `job.json` with the track id beside the file. With it empty, a catalog row offers Play only when that saved listening file already plays. Otherwise the row stays on Preview and says the command is required.
- Deezer cookie: the account's `arl` cookie, pasted under Sources (192 hex characters). The file is `deezer-arl.txt` on the data volume, mode `0600` where the filesystem allows it, and the worker reads it from there. Settings only learns that one is saved: `deezer_cookie` is true while the file exists. The PATCH body still takes `deezer_arl` to replace it, or `""` to remove it, but the value never reaches the settings table. That row stays, always empty, and every reply sends it empty. An empty box leaves the saved cookie alone. Only Remove cookie, then Save, sends the empty value. `MUSIMO_DEEZER_ARL` seeds the first start only. At startup a cookie still in the settings table (an older version kept it there, and the first-start seed puts it there) moves into the file and the row is emptied. A file that is already there wins. After that the file is what downloads use, and a removed cookie stays removed even if the variable is still set.
- `search_catalog`: `deezer` or `spotify`, default `deezer`. Deezer is the default. Spotify searches tracks and plays a preview when one exists. A download still uses the Deezer catalog. Album and artist pages stay on Deezer. The control is Search catalog, with the options Deezer and Spotify. `MUSIMO_SEARCH_CATALOG` seeds and locks it on first creation, the same way as other settings. A blank value does not lock it. Later env changes do not replace an existing row.
- Spotify app: the client ID and client secret from a Spotify developer app. The app owner needs Spotify Premium. Search returns at most 10 tracks at a time. The client secret stays on this server and is not shown again. The file is `spotify-app.json` on the data volume, mode `0600` where the filesystem allows it. Settings only learns that credentials are saved: `spotify_credentials` is true while the file exists. The PATCH body takes `spotify_client_id` and `spotify_client_secret` together to replace them, or both `""` to remove them. Neither value reaches the settings table. Those rows stay, always empty, and every reply sends them empty. An empty box leaves the saved app alone. Only Remove credentials, then Save, sends the empty values. The page says "Spotify credentials are saved.", "No Spotify credentials yet.", or "The credentials will be removed when you save." `MUSIMO_SPOTIFY_CLIENT_ID` and `MUSIMO_SPOTIFY_CLIENT_SECRET` seed the first start only, and only as a pair. At startup a pair still in the settings table moves into the file and the rows are emptied. A file that is already there wins. A removed app stays removed even if the variables are still set. The secret is not in the settings reply, job records, logs or diagnostics.
- `deezer_catalog`: on by default. Off turns Deezer search off. Album pages, track details and catalog downloads still use the catalog, because a download needs the track's details. Spotify track search does not use this switch.
- The old SoundCloud switch (`soundcloud_fallback`, or `MUSIMO_SOUNDCLOUD_FALLBACK`) is no longer a setting. On the first start with `source_order`, an on value adds SoundCloud to the end of the list. A stored row is left in the table, skipped when settings are read, and not sent to the browser. A PATCH that names it is refused. How the list behaves is in [downloads](downloads.md#catalog-source-order).
  The old playback-server address, scan mode and library number are not settings. A database from before this version drops those rows when it opens.

Library's empty state links to `/settings#library`. Any field id works as an anchor (`destination`, `naming_template`, `output_format` and the others); the page scrolls to and focuses it. Download failure links use these anchors. The liked playlist link is persisted outside the settings table in `linked_playlists` and is untouched by settings saves.

## Draft preservation

Settings keeps draft values separate from the live query data. The form renders `draft[key] ?? setting.value` so unsaved changes remain visible while background SSE events (library scans, job updates, unrelated setting changes) update the query cache. A "You have unsaved changes." status appears while the draft has keys.

When a setting changes elsewhere (another tab, another user, or the Downloads page's concurrency select), a conflict notice appears on that row showing "Changed elsewhere to X" where X is the new value. The draft is not overwritten, and the saved flag resets so a later save sends the user's intended value, not the externally changed one.

Navigation guards block in-app Link clicks and browser tab close/refresh while the draft holds unsaved keys. The blocker shows a confirmation dialog. Saving clears the draft, removes conflict notices, and shows "Saved. You can safely refresh."

See [downloads](downloads.md) for staging, formats and metadata. See [library player](player.md) for playback.

## Not yet available

Destination selection and naming templates are implemented. Notifications, source-specific budgets, proxy options and updater controls are not yet present. Secrets belong in dedicated files or encrypted storage, not this generic settings table. The YouTube cookies file, the Deezer cookie file and the Spotify app file all follow that.

Settings now includes a library scan panel with live counts, elapsed time, rescan and cancel. A cancelled scan retains the prior index.

The diagnostics export contains runtime versions, mount paths, library scan status, source test status, the player, last_download and recent events. ZIP log export and a secret-redaction layer are hardening tasks.

## Your settings

Settings has two pages behind one Settings entry, and a Server / Yours switch at the top of both. Everything above is the server's: shared by whoever opens Musimo, saved in SQLite, and locked by environment where the deployment says so. `/settings/user`, "Your settings", is the other page. Nothing on it reaches the server or another person. Names do not split the server settings. Two people can still overwrite each other, and that row still says "Changed elsewhere".

Your settings has five sections: Layout, Home page, Theme, Playback and Visualizer (the music bot pet follows them). In the Listening room the Yours half of the switch is called "Appearance & you".

**Layout** is two cards with a small picture of each, a radio group bound to `setLayout()` in `frontend/src/lib/layout.ts`. On a phone the pictures are phone-shaped and show each layout's phone arrangement (Classic's search bar and docked, cover-tinted player; the Listening room's page title and floating player and tab pill), the cards sit side by side, and the line under the heading says the choice is for this phone and a computer keeps its own. The two radios sit in a group labelled Layout. Choosing one switches the app at once and keeps the route; because the whole shell remounts, focus is put back on the chosen radio, so the arrow keys keep working. It is stored as `musimo.layout`.

**Home page** has one switch for each of the six Home sections (Continue listening, This week, Jump back in, Recently added, On repeat, Ask Octive) and a Show all button, stored as `musimo.home-sections`. A section left out of the stored map is shown, so a section added later appears for everyone until they turn it off. Both toggles apply at once and to every open tab, because they are read through `frontend/src/lib/layout.ts`, and neither is sent to the server.

**Theme** holds the cards, Follow system and the editor. While a theme is being edited, everything else on the page is not drawn: the editor's Save and Cancel ride in a bar that sticks to the bottom of the Theme section, and anything below it would let the bar scroll away at the end of the page. They come back when the edit is saved or cancelled; `e2e/phone.spec.ts` holds the bar on screen at both ends of the page. Each built-in family (Musimo, Slate, Sunset, Violet, Graphite, Windows 95) is one card showing its dark and light halves, with a moon and a sun to choose between them; a theme of your own is a card of its own. Choosing applies the theme and remembers it at once; there is no save bar. Every theme is one radio in one group, so arrow keys move between them and a screen reader hears "Slate light". The active one is marked with a tick and the word Active rather than by its border alone. "Musimo dark" is the built-in theme and the one the app falls back to.

**Follow system** is a switch above the cards. While it is on, the family you chose stays and the half is whichever one the device asks for (`prefers-color-scheme`), changing live when the device does. The moon and sun are then switched off, because the device decides, and every card shows and announces the half on screen ("Use Slate dark" on a dark device), not the half last chosen for it. A theme of your own has no other half and stays as it is. Turning it off keeps whatever is on screen. It is stored as `musimo.theme-follow-system`, and while it is on `musimo.theme-vars-system` holds both halves of the family so `public/theme-boot.js` can paint the right one on the first frame. The rule is `resolveFollowSystem` in `frontend/src/theme/follow-system.ts`.

- **Import** reads a theme file. **Duplicate and edit** copies the theme on screen, including a built-in one, and opens the editor. A built-in theme cannot be changed, only copied.
- **Edit**, **Export** and **Delete** appear on your own themes. Deleting asks once, and deleting the theme you are using puts the default back.
- **Reset to default** returns to Musimo dark, with Follow system off, without deleting anything.

The editor takes a name, a dark or light scheme, and one color per token, grouped as Surfaces, Text, Lines, Accent and Status. Each color has a native color picker and a hex field that stay in step; a half-typed hex is marked, says what it needs, and leaves the last whole color on screen. The app around the editor is the live preview, and a preview strip at the top of the editor shows the colors the page itself cannot: buttons, chips, status messages, ownership badges, rows under the pointer and text over artwork. Save and Cancel ride in a sticky bar with a line that says what is stopping a save, if anything. Save keeps the theme and turns it on. Cancel puts your saved theme back. Leaving the page with unsaved edits asks first, then does the same. Under the colors, the editor shows the contrast ratio for the pairs people read text through, names the low ones in words, and warns below 4.5:1. That warning never blocks a save. Every action leaves a short status line behind (saved, imported, deleted, cancelled) and puts keyboard focus on the Theme heading.

### Where themes are stored

In this browser only, under `musimo.theme`, `musimo.custom-themes` and `musimo.theme-vars` in local storage. They are not in the database, not in the diagnostics export and not synced. Another browser, another device or a cleared site history starts from the default. Up to 50 of your own themes are kept; at that many, Duplicate and Import are off until one is deleted. If the browser refuses to write, the page says so and the theme is not reported as saved. A list written by a newer Musimo is left alone rather than replaced, and the page says that too.

### Import and export

Export writes `<theme name>.musimo-theme.json` through the browser's own download, with characters a file name cannot hold replaced by a dash. Import takes that file back through the same validation as stored themes: known color names only, six or eight digit hex values, a name of at most 40 characters. An imported theme always arrives as a new theme, so it cannot overwrite one you already have, and it is turned on once it is read. A file that is not a Musimo theme is refused with a message and changes nothing.

### Playback

Volume levelling and crossfade for library playback, kept in this browser like the rest. **Volume levelling** is a select: Off, Track (the default) or Album (automatic). **Pre-amp** is a second select, from −6 to +6 dB in 3 dB steps, default 0, and is disabled while levelling is Off. **Crossfade** is a third, Off (the default) or 1 to 12 seconds. All three apply as they are chosen, including to a track already playing, and are stored under `musimo.replay-gain`, `musimo.replay-gain-preamp` and `musimo.crossfade`. A missing or unreadable value means the default. How the gain is worked out is in [Volume levelling](player.md#volume-levelling).

A boost (a positive tag or pre-amp on a quiet track) is never pushed past the track's tagged peak. An audio element cannot go above full volume, so the part above it goes through a gain node in the audio graph, on both library elements, which means a quiet track is lifted even with the slider at 100%. A track with no peak tag is never boosted past full volume, and previews are never boosted. See [Volume levelling](player.md#volume-levelling).

Crossfade overlaps the end of one library track with the start of the next. It is never used between consecutive tracks of the same album played in order, which run on gaplessly, or for repeat one, and it needs the next track to have loaded in time, so on a metered connection (data saver) tracks simply follow one another. How it works is in [Crossfade](player.md#crossfade). The sleep timer is not a setting: it is on the Now Playing controls, and is not kept ([Sleep timer](player.md#sleep-timer)).

Musimo does not write ReplayGain tags when it downloads yet, so only files that were tagged elsewhere are levelled. A file without the tags plays as it is, whatever these say.

### Visualizer

The third section on Your settings. Four selects: Stage size (Small or Large; Small, the default, puts the stage beside the tabs, Large gives it the page's width with the tabs below, and a phone always uses Small), Show on Now Playing (Artwork or Visualizer; it is the live view, so the stage's own control changes the same setting (the Visualizer button in Classic, the Art / MilkDrop switch in the Listening room), which a hint under the select says; a browser that has stored nothing shows Artwork), Preset (the MilkDrop presets by title, A to Z, the same options as the stage's select) and Change with the music (On, the default, or Off; see [the visualizer note](visualizer.md#changing-with-the-music)). Each applies as it is chosen and is remembered in this browser, like themes. They are the Now Playing stage's own state, not a copy: changing one here updates an open stage at once, and changing one on the stage (or with S) shows here. Where the browser has no WebGL 2, or a context could not be had, the view, preset and change-with-the-music selects are disabled and one line says why; Stage size stays available, since it lays out the artwork as well. Stored as `musimo.now-playing-size`, see [Stage size](now-playing-popout.md#stage-size). An Open Now Playing link sits under them. The keys and the state behind them are in [the visualizer note](visualizer.md#what-stays-on-musimos-side).

## Recent activity

Settings and Diagnostics reuse the same activity component. It displays the latest 100 visible events in a keyboard-focusable region with a 320px maximum height. Clear all disables while pending, reports failures and stores a persistent clear point through the snapshot the user saw. Newer events remain visible.

A run of neighbouring events of the same kind, such as a hundred "Library index updated" in a row, is one row: the event name, a count (×100) and the time range from its oldest to its newest event. The row is a button that opens the run's individual events and closes it again (`aria-expanded`). Two runs of one kind with a different event between them stay two rows, so the feed still reads as a timeline. A single event is a plain row as before. The grouping is `groupRuns` in `frontend/src/features/diagnostics/activity-runs.ts`, which folds the list the server sends; the server and the "latest 100" limit are unchanged, so a run can be cut short by that limit.

`GET /api/activity` returns events, total visible count and cursor. `DELETE /api/activity` accepts `{ "through": <cursor> }`. It validates a nonnegative integer and applies the usual same-origin write checks. Clearing affects the feed and diagnostics export, not job history or the bounded SSE replay records. This prevents clearing a panel from breaking live queue updates in other tabs.
