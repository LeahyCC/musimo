# Architecture and screen plan

The phase sections below record the implementation sequence. For current behavior, use [search and indexing](search.md), [downloads](downloads.md), [settings](settings.md) and [UI verification](ui-verification.md). Discover remains a [proposal](discover.md). The original phase gates are not a claim that every release acceptance check is complete.

## Stack

Python 3.14, FastAPI, one uvicorn process, SQLite WAL, React 19 with TypeScript strict and Vite. TanStack Router owns page and query URL state; TanStack Query owns server data and cancellation. Tailwind 4 (`@tailwindcss/vite`, imported from `frontend/src/style.css`) styles the shell and the shared controls; the remaining screens move from semantic classes to utilities in the order [the styling plan](tailwind-migration.md) sets out. Native form controls and native modal dialogs cover settings, the command palette, the queue sheet and the playlist picker. TanStack Virtual renders the download JobList above 6 cards and long track lists; `PlayerProvider` owns preview and library playback, and `PopoutProvider` is a second root context. This is a smaller dependency set than the brief: cmdk, shadcn/Base UI and Zustand are not needed. Apprise remains later work. A custom Python service is needed for processes and mounted files; the fixed self-hosted Docker requirement rules out a hosted Workers backend.

The main image builds the frontend, serves it from FastAPI, and includes FFmpeg, Chromaprint, Deno, yt-dlp and the matching bgutil plugin. Vite copies `frontend/public` (favicon, manifest) to the dist root. FastAPI serves those files as-is, then `/assets` for the JS/CSS bundle. Only the listed SPA paths fall back to `index.html`. The only helper is a pinned bgutil service with no published port. SQLite lives in a named volume. Music mounts are separately configured. The initial test mount contains no real library files. PUID/PGID ownership changes apply only to application data; never recursively chown music.

## Styling

Every screen is Tailwind 4 utilities in its own TSX file. `frontend/src/style.css` holds only the Tailwind import, the `@theme` block, the `:root` layout variables, the custom variants, the resets for bare elements and a short list of leftovers. There is no `tailwind.config.js`. [The Tailwind migration plan](tailwind-migration.md) records how the app got here and the desktop and phone layout contract a change must keep.

**Tokens and themes.** Colors are `--color-*` tokens in `@theme`, named for their job (`canvas`, `raised`, `muted`, `danger-bg`), never for a shade. Tailwind's stock palette is switched off, so `bg-raised` works and `bg-red-500` does not exist. A theme is one hex value per token. The default needs no JavaScript because `@theme` already holds it. Any other theme is written onto `<html>` (and onto the Now Playing popout while it is open) with `setProperty`, and the utilities repaint. `frontend/src/theme/` holds the token list, the built-in registry, the zod schema for stored and imported themes, the contrast helpers and the store. A built-in theme may also carry a skin, a sheet of shape rules keyed on `<html data-skin>`; Windows 95 is the only one, in `frontend/src/theme/win95.css` (see [Skins](tailwind-migration.md#themes)). `frontend/public/theme-boot.js` paints a saved theme before the first frame, so there is no flash of the default. It is a classic external script because the Content-Security-Policy allows no inline script. The policy's `script-src` is `'self' 'wasm-unsafe-eval'`: the second lets the visualizer compile MilkDrop presets to WebAssembly and allows no JavaScript eval.

**The no-raw-color rule.** No hex, `rgb()`, `hsl()` or named color anywhere outside the `@theme` block, and no arbitrary color utility such as `bg-[#17201b]`. A translucent color is an opacity modifier (`bg-accent/20`) or `color-mix(in oklab, var(--color-x) N%, transparent)`, and that includes shadows, washes and backdrops. `frontend/src/no-raw-colors.test.ts` reads every sheet (the skin's too) and every component and fails with the file and line. The only file it excuses is the theme registry.

**Primitives.** `frontend/src/ui/` has `Button`, `IconButton`, `TextLink`, `Tag`, `StatusChip`, `Ownership`, `Panel`, `EmptyPanel`, `ErrorBanner`, `InlineError`, `Field`, `FieldSelect`, `Kbd` and the section heading class strings. Each primitive sets `data-ui`, and its touch size (`coarse:` 44px) lives inside it. Use `className` on a primitive for layout only. A size or color that differs by context becomes a variant (the round footer play button is `IconButton variant="play"`), because `cx` joins strings and does not settle two utilities fighting over one property. For an element a component cannot wrap, such as a routed `<Link>`, use a `*ClassName` helper and set the same `data-ui` by hand.

**Breakpoints and variants.** Three named widths: `max-phone:` (under 768px: bottom bar, mini player), `max-tablet:` (under 1100px: narrow sidebar) and `wide:` (1500px and up). They are in rem and the stock `sm` to `2xl` are reset, so they sort in the right order. `coarse:`, `fine:` and `no-hover:` cover pointer and hover, and Tailwind's `motion-reduce:` covers reduced motion. The few handwritten media queries read the same edges through `theme(--breakpoint-*)`, so the `:root` variables and the utilities switch at the same pixel. Layout measurements (`--sidebar-width`, `--topbar-height`, `--nav-height`, `--player-height`, `--progress`, `--safe-*`) stay plain custom properties, because `player.tsx` writes one and several `calc()`s add them up.

**What stays handwritten.** Only what a utility cannot reach or must lose to: the focus ring, the native color swatch, `meter` vendor bars, the virtual list height, the card link's `::after` hit area, dialog `::backdrop`s, the phone seek bar's vendor pseudo-elements, the fullscreen and popout stage, the reduced-motion reset and the coarse-pointer 16px text rule. The last group sits outside every cascade layer on purpose, so it wins over any utility. Bare element resets live in `@layer base`, so a utility on the element wins over them. Do not add `@apply` piles. A new screen rule goes on the element.

**Styling a new screen.** Utilities on the elements, joined with `cx` when a class depends on state, and one state or the other in a ternary, never a base class plus a conditional one for the same property. Reach for a primitive before a raw element, and for a variant on it before a `className` override. Widths through `max-phone:`, `max-tablet:` and `wide:`, pointer through `coarse:` and `no-hover:`. Nothing new in `style.css` unless it is on the leftover list. Before it ships: the phone spec, the screen's own spec, `e2e/themed-walk.spec.ts` (add the route to it), and one pop-out of Now Playing. The full rules are under [Testing rules](tailwind-migration.md#testing-rules-for-every-styling-pr).

**Adding a built-in theme.** Add one object to `BUILT_IN_THEMES` in `frontend/src/theme/themes.ts` with an id, name, scheme and a value for every token. `contrast.test.ts` fails it on any pair in the editor's readability report under WCAG AA, then walk the app under it the way `e2e/themed-walk.spec.ts` walks the light fixture. Leave `musimo-dark` equal to the `@theme` block: `themes.test.ts` compares them.

**Adding a token.** Only when no existing role can express the color. Give it a role name, not a screen name. Add it to `@theme` in `style.css`, to `COLOR_TOKENS` in `frontend/src/theme/tokens.ts` with a label and group for the editor, to `musimo-dark` in `themes.ts` and to the light fixture in `e2e/theme-fixtures.ts`; if text is read through it, add the pair to `CONTRAST_PAIRS` in `frontend/src/theme/contrast.ts` so the readability report sees it; then list it in the token table in [the migration plan](tailwind-migration.md). A saved theme that predates the token still loads: the schema fills a missing token from the default.

## Storage

Opening a database newer than this build supports closes the SQLite connection before refusing startup. This lets Windows release the file for recovery instead of retaining a handle on the rejected database.

The database has `settings` and `job_events`. Schema versions use SQLite user_version. One writer connection is protected by a lock; write transactions use BEGIN IMMEDIATE. Snapshot data and event cursor are read under the same lock. Settings and source-health mutations commit with their corresponding events. Library scan status also commits with its event; file-index writes are grouped into throttled progress notifications. This prevents missing state between a snapshot and SSE subscription.

The database also has `library_roots`, `library_files`, `library_state`, FTS5 and `search_cache`. Preserve multiple paths for the same recording. Cache by Deezer request path, query, result kind and page; L1 LRU with TTL, L2 SQLite. Catalog filters and sort operate on loaded provider results, so they do not create separate upstream cache entries. Library track browsing is the exception: see [library player](player.md) for the bounded whole-library snapshot its filters, sort and totals read from. Cover filenames found while scanning are stored in `library_covers` (folder, path, size, modified time), created on startup, so that snapshot does not list the music folders. The process builds the snapshot in the background at startup and again after the index changes. No market selection is implemented. Use lightweight batched ownership joins, never file reads from result rendering.

The database includes `jobs`, `batches`, `sources_health` and artifact manifests. Jobs hold catalog identity, target root, requested quality, selected source, candidates, attempts, desired action, observed stage, progress, final path and codec/bitrate. A partial unique index prevents duplicate active jobs using the specified catalog/id/format/bitrate/root key. Store bitrate as a non-null canonical value to avoid SQLite NULL uniqueness gaps. History persists after the active slot is released. The `linked_playlists` table stores the liked playlist link. Schema version 4 adds `source_control`, one row per download source with its pause flag and blocking failure count; the upgrade copies the old single `queue_control.source_paused` flag and count across as the `youtube` row, and `queue_control` keeps only the global pause. Schema version 5 adds `pace_started` and `pace_until` on `queue_control`, the count and end time of a pause between groups of downloads. Schema version 6 is the local player. It adds song, tag and file columns on `library_files` (`song_id`, `added_at`, track, disc, year, genre, album artist, compilation, ReplayGain, suffix, content type, bitrate, sample rate, bit depth, channels, art, play count and last played) and the tables `playlists`, `playlist_songs`, `artist_favourites`, `play_queue`, `play_queue_songs` and `library_revision`. The upgrade assigns a `tr-` id to each existing file, clears `waveforms` (those rows were keyed by the old playback ids) and deletes the old playback-server settings. This application opens version 12. An older build refuses it. Rolling back after the upgrade needs the backup taken before it. The `waveforms` table caches the Now Playing seek bar's peaks, one row per song: `song_id` (primary key), a `fingerprint` and 800 bytes of `peaks`. The fingerprint is an algorithm version plus the file's size and modified time, so a changed file replaces its row on the next request. Reads and the upsert go through `Store.waveform` and `Store.save_waveform` on the one writer connection, under the lock and `BEGIN IMMEDIATE`. The table is created by `CREATE TABLE IF NOT EXISTS` in the same block, so an existing database gains it on its next start. Version 6 clears its rows once. Migration and recovery: nothing to migrate, and because it is only a cache, `DELETE FROM waveforms` (or dropping the table) is a safe reset that the player refills on demand. A row is about 1 KB, so a 50,000 song library adds roughly 50 MB at most. Schema 9 adds `audio_profile`, one measured row per song and recipe (status, the file's size and modified time, tempo, energy, a vector and its length, a detail), and `audio_job`, the queue the audio worker leases from. Both are keyed by `song_id` and recipe, both go with a song's playlist and queue rows when it leaves the index, and dropping either table is a safe reset like the waveform cache: the worker refills them from `scripts/enqueue_audio_trial.py`. See [song characteristics](audio-profile-spec.md).

Events have an increasing ID, type, payload and timestamp. Retain a bounded replay window; a stale or future cursor receives a reset event and must reload the snapshot. SSE heartbeats contain no IDs. One stream per browser tab; no per-track timers. Uvicorn's graceful shutdown is bounded at two seconds so open SSE connections cannot indefinitely hold a restart. File logs and exported diagnostics must redact credentials and token-bearing URLs.

## APIs

Music bot (api/music_bot_api.py, library/music_bot.py, library/engine.py, library/engine_contract.py, library/proposals.py):

- `GET /api/music-bot/models`: connection test and installed model names from the configured Ollama server.
- `POST /api/music-bot/chat`: one schema-constrained Ollama call, followed by service-side validation and resolution against the existing SQLite-backed player view. It returns a search plan and real track cards, or a clarification, unsupported request or transport command. It never changes playback or writes the queue. An optional `scope` (`library`, `proposal` or `queue`) is where the person chose to look; when set it replaces the model's own reading of the words for that request. A clarification or unsupported reply can carry up to three `suggestions`, short follow-ups the chat offers as one-tap replies; the server empties them on every other action, and the audio-analysis refusal supplies its own tag-based ones. A library search puts the songs the server remembers showing (see [Shown-song memory](#shown-song-memory)) after the songs that fit as well and never excludes them. The body has no say in it: a `shown_ids` sent here is replaced by the server's memory, so the browser no longer sends one. `generation_seed` (0 to `2**53 - 1`, optional) repeats a library selection; without it the server draws a fresh seed. The reply returns the `generation_seed` it drew with, and null when no library selection was drawn (a refinement, a question or a command). The browser sends no seed. See [Broad selection](audio-profile-spec.md#broad-selection).
- `POST /api/music-bot/validate`: rechecks the proposal's filters, play history, likes, safe file availability and, when a recipe is on, the tempo, energy and vector gates before a browser action. A row that went stale is 409, the same as a vanished file. The reply carries the reference and current song ids the plan was measured against, and the browser sends them back here, so a "calmer than this" proposal can still be checked after the player has moved on. It does not take or check the generation seed, the shown songs or the order.
- `POST /api/music-bot/intent`: the structured entry point, with no model call. The body is a versioned canonical intent: `contract_version` (4; 1 to 3 are still accepted, with 1 and 2 meaning an intent without `total_length`, which is all they could say, and 3 or lower meaning an omitted `context.shown_ids` is an empty list), `action` (`search`, `pause`, `resume`, `skip`, `clarify` or `unsupported`), `scope`, `filters` (the hard filters the search plan has, with the empty filter as the default), `seed`, `context` (`current_id`, `reference_id`, `proposal_ids`, `queue_ids`, `shown_ids`) and, for a clarification or refusal, `explanation`. `filters.total_length` (version 3) is `{"mode", "seconds"}`; see the total-length bullets below. There is no follow-up merging; the intent is already the whole request. `library/engine.py` turns it into the existing `SearchPlan` and `BotRequest` and calls `MusicBot.resolve`, so exact identity, the artist cap, the named-artist exception, the relevance window, missing-file skipping and the refinement order are the chat's own. The reply has `status: ok`, `ids` (the ordered song ids, which stay the opaque `tr-` ids), `tracks`, the totals and summary, `duration` (the total-length report, null without `total_length`), the `seed` drawn, the `intent` it ran with that seed filled in (so posting it back repeats the selection without editing), the `plan`, `state_changed: false` and a `snapshot`. The snapshot is `engine_version`, `contract_version`, the seed, and a digest of each other input the ids depend on: the catalogue (revision, song count, digest of the tags, durations and file stamps the filters read), play history, likes, the recipe ids and per-row state of each audio profile, the reference and current song, the local day in the store's music timezone, the music folders and whether each is enabled, and the shown list (the memory revision it was read at, count, unknown count, digest), plus an `id` over all of it. Each row is hashed as JSON, so a tag holding a separator cannot make two catalogues look alike. Embedding vectors are not hashed themselves; the recipe id and each row's file stamps stand for them. The same intent and the same snapshot give the same ordered ids. The engine reads the snapshot before and after `resolve`, repeats the call up to three times if it moved, then answers `snapshot_changed` (409). The files on disk are not part of it; a song whose file is gone before the next rescan is skipped, as in chat, so two equal snapshot ids can still differ by a vanished file. `ENGINE_VERSION` changes with any rule that orders or chooses songs; version 2 added the total-length search, and engine version 3 made a library search with no `context.shown_ids` read the server's memory of presented results. That is also contract version 4, since an omitted list used to mean none: for an intent that says version 4, `context.shown_ids` omitted (or null) means that memory, read in each of the engine's attempts and named in the snapshot as `shown.memory_revision`, so the same seed against another memory is another snapshot id. For an intent that says 3 or lower, omitted still means an empty list, the memory is left unread and `memory_revision` is null, so an older client's request is unchanged. A list, even an empty one, is used as given at any version, the memory is left unread and `memory_revision` is null. Other scopes read no list. The echoed `intent` keeps `shown_ids` as sent, so posting it back reads the memory as it is then, and a repeat that needs the old list sends it. A snapshot adds roughly 30 ms per capture at 50,000 synthetic songs, twice per request.
- A refusal is typed JSON, `{"status": "error", "error": {"code", "message", "fields"}}`, and never a looser search. Codes: `malformed_request` (400, or 413 over 256 KB), `unsupported_version`, `unknown_field` (any field this version does not define, including `total_length` under version 1 or 2), `selection_too_large` (a `limit` over 500, or more than 500 `proposal_ids` or `queue_ids`; the message says the limit and nothing is cut), `invalid_intent` (a wrong value, a blank name, a reversed range, ids beside the wrong scope, a `seed` or `shown_ids` outside a library search, filters on a pause, `total_length` beside a nonzero `target_seconds`), `unsupported_capability` (tempo, energy or sound with their recipe off), `unsupported_constraint` (a negated description such as "no vocals", a description beside `similar_to_current`, an exact BPM with `tempo_min` equal to `tempo_max`, which the chat widens by 10 either side, or `artists`/`genres` beside `similar_to_current` with no embedding recipe, which the chat replaces with the reference's tags; the chat drops or rewrites these, this path refuses them), `unknown_song` (a `current_id`, `reference_id`, `proposal_ids` or `queue_ids` entry that is not in the library), `no_selection`, `missing_reference`, `reference_unmeasured` (a comparison or sound similarity whose reference has no fresh measurement, which the chat reports only as words beside an empty list), `engine_rejected` (anything else `resolve` refused), `snapshot_changed` and `internal_error` (500, an unexpected failure, in the same envelope). `shown_ids` is memory, so an id since removed is counted in `snapshot.shown.unknown`, not refused. Neither success nor refusal plays, queues, saves or records anything, this route writes no receipt, and a browser that cancels gets 499. `pause`, `resume` and `skip` are reported only; the browser applies them. The player is still driven by `bot-chat.tsx` alone.
- `POST /api/music-bot/proposals`: the intent route, with the result kept. The body is a search intent; anything else (a pause, a skip, a question) is `invalid_intent`, because direct commands stay immediate. It runs `Engine.run` and stores revision 1. The reply is `{"status": "ok", "proposal": {...}, "tracks", "missing_ids", "state_changed": false}`. `proposal` has `id` (`pr-` plus 16 hex), `revision`, `latest_revision`, `created`, `intent` (as run, with the drawn seed), `seed`, `ids` (the full ordered list), `total_seconds`, `shortfall_seconds`, `duration` (null for a search without `total_length`, and for a revision stored before version 3), `summary` and the full `snapshot`. `tracks` are the cards for those ids from the library as it is now, and `missing_ids` names any id since removed. `proposal` also carries `overview` and `sample` (`library/proposal_summary.py`), worked out on every read from the songs as they are now, so the full `ids` list stays the whole proposal and these are the compact view of it. `overview` keeps three kinds of fact apart. `requested` is the scope and the filters the intent set, nothing else. `measured` is read from the songs: `track_count`, `total_seconds` (whole-track lengths summed, ignoring a missing, zero or nonfinite length), `artist_count`, `genres` (name and count, most songs first, each song once per genre) and `year_range`. When a scalar recipe is on, `measured.audio` adds the tempo and energy ranges from rows measured from the file as it is now, with `tempo_coverage` and `energy_coverage` as `{measured, total}`; with no recipe it is null, and a genre name never stands in for a measurement. `unknown` counts what could not be read: songs with no usable length, year, genre or artist, songs since removed (`missing_tracks`) and, with a recipe on, songs with no fresh tempo or energy. A gap is reported as unknown, never as zero or as a negative. `sample` is `{ids, complete}`. At 12 songs or fewer it is the whole list in order and `complete` is true. Over 12 it is six songs from the proposal in the proposal's order, chosen one at a time for a new artist first, then the most genres not yet shown, then a length band (thirds of the proposal's own known lengths) not yet shown, then a hash of the proposal id and song id. It reads tags and lengths only, so a new measurement cannot change it, and one revision gives the same sample while its songs are unchanged. It does no model call, scan or length solving.
- `POST /api/music-bot/proposals/{id}/revisions`: refine. The body is `{"revision": n, "intent": {...}}`, where `n` must be the latest revision (an older one is `revision_superseded`, so two refinements of one revision cannot both land). A `proposal` scope refines that revision's songs in their order and the server supplies them, so `context.proposal_ids` in the body is `invalid_intent`. A `library` or `queue` scope searches again under the same proposal id. The new revision is stored and the old one stays readable. The reply is the same shape as create.
- `GET /api/music-bot/proposals/{id}?revision=n`: one revision, the latest without `revision`, in the same shape. Create, refine and read write only the proposal tables: no playlist, queue, playback or history.
- `POST /api/music-bot/proposals/{id}/commit`: `{"contract_version": 2, 3 or 4, "revision", "operation_id", "target", "older_revision", "repeat"}`. `target` is `{"kind": "playlist", "name"}` (1 to 200 characters after trimming, the playlist routes' rule) or `{"kind": "queue"}`. `operation_id` is made by the client, 8 to 80 of `A-Z a-z 0-9 . _ : -`. The commit never runs selection again. In order: an `operation_id` that already has a receipt returns that first receipt with `replayed: true` and writes nothing (used for another proposal, revision, target or playlist name, it is `operation_conflict`); the receipt lookup is repeated under the store lock just before the write, so two requests with the same id at the same time save once and both get that receipt; an unknown proposal or revision is 404; a revision that is not the latest is `revision_superseded` unless `older_revision` is true; an empty revision is `empty_proposal`; then every check stored with the revision is taken again (below), and any difference is `proposal_stale` (409) with one field per change (a song that is gone or unplayable now is always one, even if the stored check already said so), such as `songs.tr-... / The file is unavailable`, so the client refreshes the preview. Songs are never substituted. A revision already committed to the same kind of target under another operation id is `already_committed` unless `repeat` is true. A `playlist` target then saves a new playlist with exactly those ids in that order, in the same transaction as the receipt. A `queue` target writes only the receipt: the browser owns the live queue and applies the ids through `PlayerProvider`, so the server never claims audio started. The reply is `{"status": "ok", "receipt": {...}, "replayed": bool}`. The receipt is `operation_id`, `proposal_id`, `revision`, `target`, `ids`, `status` (`saved` for a playlist, `ready_for_player` for a queue, never `playing`), `playlist_id` and `playlist_name` (null for a queue) and `created`. An error or a cancel (499) writes no receipt. A cancel is checked just before the write; a client that drops after the write but before the reply gets the receipt by retrying the same operation id. A proposal or revision pruned between the checks and the write is `proposal_not_found` and nothing is written.
- The checks a commit repeats are what the approved songs depend on, read right after selection (and refused with `snapshot_changed` if the library moved in between): for each song, that it is still in the library with a file in an enabled folder, and a digest of its file stamps, tags and length; its play count and last play only when `history` or `exclude_played_days` is set; whether it is liked only when `favourites` is set; its audio profile row and the recipe id only when a tempo, energy, sound or embedding similarity filter is used; the local day only with `exclude_played_days`; and the same song checks for the reference of a comparison. A song added elsewhere, or a like on a song not in the proposal, does not make it stale. The library revision is read again under the store lock just before the write; a scan in between is `snapshot_changed`.
- New codes on these routes: `proposal_not_found` and `revision_not_found` (404), `revision_superseded`, `proposal_stale`, `already_committed`, `operation_conflict` and `snapshot_changed` (409), `empty_proposal` and `invalid_request` (422, a commit or refine body that does not validate). An unknown field in any body is `unknown_field`, and a commit with `contract_version` other than 2, 3 or 4 is `unsupported_version` (the commit body did not change in 3 or 4).
- `GET /api/music-bot/memory`, `POST /api/music-bot/memory/shown`, `DELETE /api/music-bot/memory`: the shown-song memory below. Each answers `{"status": "ok", "profile": "default", "revision", "results", "songs", "recorded", "reason"}`. The POST body is `{"proposal_id", "revision", "memory_revision"}`, and the songs come from that stored revision, never from the body. `memory_revision` is optional: the memory revision the card was built against, which is `snapshot.shown.memory_revision` of that revision, and omitted or null for a result built without the memory. `recorded` is true only when this call added a result. `reason` is empty, or `forgotten` when the result was not recorded because the memory was forgotten after the revision it was built against (see Forget below); that is a 200 answer, not an error, and the reply shows the memory as it is. A revision that is not a library search (a refinement of a proposal or the queue), or has no songs, answers 200 with `recorded: false` and changes nothing. An unknown proposal is 404 `proposal_not_found`, and a body that does not validate is 422. A client that goes away before the write gets 499 and nothing is recorded. DELETE forgets the shown songs for every device and writes nothing else.
- `GET /api/music-bot/capabilities`: the registry for the current settings, with `supported_versions`. It lists the actions, scopes and filters `resolve` supports today, with tempo and energy available only while a scalar recipe is on and `sound` only while a text-aligned embedding is, lists `proposal_commit` as available (a playlist or a hand-back to the browser's player, never playback), lists `total_length` as available, and marks `audio_certainty`, `persona` and `external_catalogue` as not available. `target_seconds` is listed as it works: the walk stops once the total reaches it. The old `duration_comparators` entry is gone; `total_length` replaces it. A new filter or context field must be registered; a test fails otherwise.
- Total length (`library/duration.py`, version 3 intents only; the chat never sets it and its `target_seconds` fill is unchanged). `mode` is `under` (sum strictly less than `seconds`), `at_most` (less than or equal), `at_least` (equal or more, as small an overshoot as the search finds), `over` (strictly more) or `about` (the closest total within 300 seconds either side). An unqualified "60 minutes of" is meant to be `about`. `seconds` is 1 to 86,400. Length is the sum of the stored song lengths, compared in whole milliseconds; no crossfade or gap is estimated. It cannot sit beside a nonzero `target_seconds`. `min_seconds` and `max_seconds` stay limits on each song.
- A song whose stored length is unknown, zero or not finite cannot count towards a total, so it is left out and counted in `duration.unknown_length`. Without `total_length` it can still be found, as before. The scan stores a length a broken header reports as infinite or not a number as 0, unknown (`track_length` in `library/tags.py`), and a row scanned before that is read back as 0, so no reply carries a length JSON cannot encode. A `target_seconds` fill skips such a song too. A playlist's total in the playlist list is still summed in SQL, so an infinite length stored by an older scan reaches it until that file is scanned again.
- The search walks the same order `_fill` would (the seeded draw for a library search, the person's order for a refinement), takes the first 600 songs that pass the per-song checks and have a playable file (`CANDIDATE_CAP`), and runs a depth-first search over them: try each song before skipping it, so the first path is a plain greedy fill in that order, then swap the later songs first. It stops after 50,000 steps (`WORK_LIMIT`, one step is one song tried at one position), never on the clock, so the same seed and snapshot give the same set. Ties go to the songs earlier in the walk. The artist cap, the duplicate-title rule and the named-artist exception are rules of the search, as in `_fill`; a refinement applies neither, as in `_fill`. The result is not claimed to be the best total the library holds. Measured on 600 synthetic candidates, one search is 5 to 15 ms and the worst request (three searches) about 20 ms; building the shortage bound reads every match's title and artist key, about 75 ms per 50,000 matches.
- When the target is not met, nothing is loosened: genres, exclusions and every other filter stay. With a floor (`about`, `at_least`, `over`) the result is the longest selection found below it. With a ceiling (`under`, `at_most`, `about`) the shortest selection found at or past it is `duration.alternative` (`ids`, `tracks`, `total_seconds`, `deviation_seconds`), for the person to accept; a client accepts it by asking for those ids as a `proposal`-scope search. One long mix and nothing shorter gives no songs and the mix as the alternative; it is never cut. `unmet_reason` is `proven` when a bound over every eligible song rules the total out (the longest any selection could be under the cap and title rules is below the floor, or the shortest song is past the ceiling) or when the search finished over all of them; otherwise it is `not_found`, the limit was reached or the 600-song cap left songs out. Each of the up to three searches (the target, the shorter fallback, the longer alternative) has its own 50,000-step limit.
- `duration` is `mode`, `target_seconds`, `window_seconds` (300 for `about`, else 0), `total_seconds`, `deviation_seconds` (total minus target), `met`, `unmet_reason` (`""`, `proven` or `not_found`), `unknown_length`, `candidates`, `candidate_cap`, `candidates_capped`, `work`, `work_limit`, `search_complete` and `alternative`. Every total and deviation in it, and the reply's `total_seconds` and `shortfall_seconds` for a total-length search, come from the same whole milliseconds the search compared, so `met` and the numbers always agree (three songs of 1200.0004 s are reported as 3600.0, at most an hour, not 3600.0012). `shortfall_seconds` is the target minus the total when a floor is unmet, else 0. The summary says the same in words. The constants are pinned beside `ENGINE_VERSION` in `tests/test_engine.py`.

The bot service uses the existing `httpx` client, with no redirect following or retries. Model discovery and capability lookup each have an eight-second wall-clock deadline; inference has 90 seconds. Each response is capped at 128 KiB. Before inference, `/api/show` determines whether `thinking.values` supports boolean `false`. Only then does the request include `think: false`; missing metadata or named levels retain the model default. Every chat includes `keep_alive: "60s"` and `num_ctx: 8192`. These are per-request controls, independent of server restart settings. One chat request runs at a time and disconnect cancels its HTTP request, including capability lookup. Prompts are capped at 2,000 characters, history at eight messages, tag context at twelve songs per group and selections at 500. Every in-scope song is gated and ordered; there is no candidate ceiling, and files are checked only while the list is being filled. A structured `total_length` search is the exception: it reads at most 600 playable songs from the front of that order (below). The model cannot submit SQL, paths or song ids in its plan. Library tags are data, never instructions. Model output is untrusted even when it matches the schema: reference-artist removal and known unsupported comparative audio requests have service guards.

Follow-up plans name explicit filter changes, artist exclusions to withdraw, scope and a count of songs to add. The service inherits unchanged filters, accumulates artist exclusions and requires withdrawal language before relaxing exclusions. Adding songs retains eligible proposal entries in order and appends distinct matches. Clarification text cannot become a playable search merely because a model supplied the wrong action.

The browser uses `PlayerProvider` for every playback action. A generation guard discards cancelled or superseded responses, and a queue stamp rejects stale proposals. The chat (`features/music-bot/bot-chat.tsx`, `proposals.ts`) turns each search answer into a proposal revision from the answer's own plan: the plan's filters, the seed the chat drew and the songs it was made against become the intent, and the card then shows what the server stored. A follow-up becomes the next revision of the open proposal; adding songs and removing one store the exact list as a new proposal (a `proposal` scope intent), because the intent has no way to say either. Every request names contract version 4, which create and refine accept (1 to 4) and commit accepts (2 to 4). It must be 4, since a lower version reads no shown-song memory, so a stored intent an older build left is sent again with the current version. The chat never sets `filters.total_length`, but a stored intent can carry one, so a refresh sends it back unchanged. Play, queue and save commit that revision with a fresh operation id made in the browser, kept for a retry and replaced only after a definite answer. A queue commit waits for the receipt and applies the receipt's ids through `PlayerProvider`; it is never claimed as playing. A commit that gets no clear answer (network error, timeout, 5xx, 499, or a 200 whose body is not a receipt) is asked again with the same id, once at once and then on request, and no other attempt is offered until it settles. `proposal_stale` shows what changed and offers a refresh as the next revision. `POST /api/music-bot/validate` is still used for the one-song Play this song and is kept for older clients. The songs it has shown are the server's memory, not the tab's: once a search answer's card is on screen the chat reports that revision (`POST /api/music-bot/memory/shown`), never the song ids, and never for a request that was cancelled or superseded before it got there. Chat settings shows what the server remembers and a Forget shown songs control. The old `musimo.music-bot.shown` session key is deleted on load so a stale copy cannot disagree. Clear chat empties the conversation, the open card and the preview in this browser and leaves the server's memory alone, because that memory is shared with the owner's other devices and has its own control. The open revision is kept in `musimo.music-bot.preview`. The conditional Undo snapshot includes the shuffle continuation and edited-source state. Queue saves have eight-second request deadlines and coalesce to one active request plus one pending snapshot. `POST /api/player/queue/writer` allocates an epoch; `PUT /api/player/queue` supplies that epoch and a monotonically increasing sequence. SQLite rejects stale writes with HTTP 409 inside the same transaction as the queue replacement. A replaced browser writer requires refresh. Legacy unversioned writes remain supported and invalidate tokened writers.

Schema 8 adds `writer_epoch` and `write_sequence` to the single `play_queue` row, without rewriting songs, listening history, playlists or queue entries. The counters survive restart. Tests upgrade populated schema 6 and reopen twice, alongside the earlier migration tests. Older binaries refuse the newer schema; downgrades need a pre-upgrade database backup. Settings and existing play counts/last-played timestamps stay in SQLite.

Schemas 10 and 11 add the music bot's proposal tables. `bot_proposals` is one row per proposal: `id`, `latest` revision, `touched` (a use counter) and `created`. `bot_proposal_revisions` is keyed by proposal and revision and holds the intent as run (JSON), the effective `seed`, the ordered `song_ids` (JSON), the full `snapshot`, the per-song `checks` a commit repeats and the totals and summary. `bot_receipts` is keyed by `operation_id` and holds the proposal, revision, target and the receipt JSON. Revisions reference their proposal with `ON DELETE CASCADE`. Receipts have no foreign key: they outlive their proposal, so a retried commit still replays after the proposal is pruned. The store keeps the 20 most recently used proposals (`PROPOSAL_LIMIT`; creating, refining or committing counts as use) and the 20 newest revisions of each (`REVISION_LIMIT`), pruned in the same transaction as each new revision, and the 200 newest receipts (`RECEIPT_LIMIT`), pruned as each receipt is written. A pruned proposal answers `proposal_not_found`; a retried commit for it still returns its receipt while the receipt is kept. Schema 11 rebuilds `bot_receipts` without the foreign key that version 10 gave it, keeping every row and its order. Neither upgrade changes any other table. Recovery: the tables hold suggestion state, not history. `DELETE FROM bot_proposals` (the cascade takes the revisions) drops open previews, and `DELETE FROM bot_receipts` drops the memory of past commits, which means a commit retried after that saves again; neither touches a playlist. To open the file with a schema 9 build, drop `bot_receipts`, `bot_proposal_revisions` and `bot_proposals`, then set `PRAGMA user_version=9`; nothing else in the file changed.

Schema 9 is [song characteristics](audio-profile-spec.md): the `audio_profile` and `audio_job` tables, the internal lease above, the optional worker under the `analysis` profile, and the ranker. A library search ranks its matches by one key only: cosine for "more like this" or a sound phrase once an embedding recipe is named, play count only for a "more familiar" request, and otherwise none, so every match fits equally. It then draws the order under a generation seed (`backend/library/selection.py`): a uniform shuffle when there is no key, and a draw weighted by fit from a window near the best matches when there is one, listed best fit first. Refining a proposal or the queue keeps the person's order; nothing is drawn or sorted, even with a rank key. In a library search, or when songs are added to a proposal, a repeated title by the same artist is kept once and an artist fills at most two places unless the request names it; refining a proposal or the queue only filters it. Two settings name the recipes the bot may read, `audio_scalar_recipe` and `audio_embedding_recipe`, both empty. An empty recipe means the bot ignores any rows for it: the prompt still refuses mood, energy, tempo, instruments and vocals, a plan that filled those fields anyway is turned into the same refusal, and "more like this" still copies the reference song's tags. With `tempo-energy-v1` named, tempo and energy become hard gates on songs with a fresh row and the summary states the recipe's coverage; with an embedding recipe named, "more like this" and a sound phrase rank by cosine. No recipe is named until its listen passes. See [player behavior](player.md#music-bot) and [review fixes](music-bot-review-fixes.md).

## Shown-song memory

A library search puts songs it showed lately after equally fitting ones and never excludes them. That list is suggestion memory kept by the server for one default listener profile, so it survives a restart, a closed tab and a second device. It is not a taste score: play counts and skips never become a like or a dislike, and nothing here changes how a search ranks by fit.

- **What is kept.** The last three presented library results (`SHOWN_RESULTS`), and a search reads at most 500 distinct songs from them, newest first (`SHOWN_IDS`, the same bound the tab used). Each result holds at most 500 ids. A song in two results counts once.
- **When a result is recorded.** Only when the browser says a stored revision was shown (`POST /api/music-bot/memory/shown`), and only if that revision is a library search with songs. The key is `proposal:revision`, so the same presentation recorded twice is one entry, including a late duplicate after its result has aged out (the last 50 keys are kept, with no song ids in them). A cancelled or superseded generation never reaches the call. A refinement of a proposal or the queue, a question, a command and an empty result are not recorded, as before. Creating a proposal does not record it either: it is a preview until shown.
- **Revision.** `bot_memory.revision` rises by one on every change, including every forget, even of an empty memory. A search names the revision it read in its snapshot, so the same seed over another memory is another snapshot id. A stored proposal keeps the snapshot it was built with and its ids. A commit never selects again and does not check the memory, so recording, a restart or Forget never alters or stales an approved proposal. A refinement in library scope reads the memory as it is then.
- **Updates.** One `BEGIN IMMEDIATE` transaction under the store lock reads the row, applies the change, trims to the bounds and writes it with the new revision, so overlapping writes each land whole, in either order, and none corrupts the list.
- **Forget.** `DELETE /api/music-bot/memory`, from Chat settings, empties the memory for every device and says so. It leaves play history, likes, playlists and proposals alone. It keeps the presentation keys so a delayed duplicate cannot bring a forgotten result back. It also records the revision it produced as the last forget (`bot_memory.forgotten`). A presentation that was on its way from another device when Forget was pressed carries the memory revision its card was built against, and is not recorded when the last forget is later than that revision. The reply says `recorded: false, reason: "forgotten"` and the browser does nothing more, because the card was made before the person asked to forget. A card built after the forget carries the new revision and is recorded. A result with no revision to compare is recorded as before.
- **Clear chat** empties this browser's conversation only. The memory belongs to the profile and has its own control, so a tab-local action does not silently change what the owner's other devices remember.
- **Profile.** There is one profile, `default`. The key is a row name, not authentication, and there are no accounts. Anyone who can reach the server can read or forget it. Several listeners are out of scope.

Schema 12 adds `bot_memory` (`profile`, `revision`, `generations` as JSON `[{key, ids}]`, `acked` as a JSON list of keys, `changed`, `forgotten`, the revision of the last forget) with one `default` row at revision 0. The upgrade creates it empty: the old copy lived in a browser tab and is not carried over. Neither upgrade touches any other table. Recovery: the table holds suggestion state only. `UPDATE bot_memory SET revision = revision + 1, generations = '[]', forgotten = revision + 1` forgets the songs, as the control does, and is safe at any time. A deleted row reads as an empty memory at revision 0 and is written back on the next change, but that reuses revision numbers a snapshot may already name, so prefer the update. To open the file with a schema 11 build, run `DROP TABLE bot_memory` then `PRAGMA user_version=11`; nothing else in the file changed.

## Job state machine

```text
queued -> matching -> downloading -> converting? -> tagging -> moving -> scanning -> done
   |          |            |
   +----------+------------+-> pausing -> paused -> queued (resume artifact)
   |          |            |
   +----------+------------+-> cancelling -> cancelled

any active stage -> retry_wait -> queued
any active stage -> failed -> queued (manual retry)
```

Podcast episodes and pasted links skip `matching` and go straight to `downloading`. A catalog track walks `source_order`. The card names the first row that can run when the job is queued. The worker reports the source it is asking before the search, and a block pauses that source, including a search that failed before a file was saved. A hand pick (`hand_picked`) stays on that recording. Retry of anything else clears the automatic pick and walks the list again. Conversion is skipped when possible; remuxing is recorded distinctly from lossy encoding. A pause during tagging either finishes that artifact or restarts tagging later, never continues a corrupt partial tag write. Pause intent remains durable through process exit and container restart. A restart reconciles active stages against the manifest before dispatch. Errors retain stage, code, retryability, a redacted tool tail and tool version. Three consecutive blocking errors (`SOURCE_BLOCKED`, `POT_MISSING`, `JS_RUNTIME_MISSING`, `COOKIES_EXPIRED`) pause one source, not unrelated healthy sources: the error names its source, the count and pause are kept per source in `source_control`, a completed download from that source resets its count, and a catalog song still starts while any row in its list can run. `GEO_RESTRICTED` and a podcast host's refusals never count toward a pause. Disk-full/unwritable jobs require a successful destination probe before retry.

## Search and catalog implementation

See [search and indexing](search.md) for API contracts, cache limits, ownership matching, watcher behaviour and the tested journey. Search uses independent concurrent track/album/artist HTTP requests. Each section paints when its request completes; catalog results do not need an additional SSE protocol. The existing SSE stream carries durable library updates. Track downloads, album batches and reviewed artist album selections are available. Pasted links have a server API and a review sheet in the search box (see [search](search.md#pasted-links)).

## Download worker implementation

See [downloads](downloads.md) for durable job state, worker control, publication and verification. Each job owns a child process group. SQLite records the full state and replay event in one transaction; completed audio is published without overwriting existing files. The local Docker Desktop mount uses the tested hard-link fallback because it rejects Linux no-replace rename flags.

## Library player

See [library player](player.md). Musimo plays the files in its music folders. Browsing, the stream, cover art, lyrics, playlists, favourites, play counts and the saved queue come from that index (`backend/library/player.py`). A finished download is indexed by `Library.index_published`, which is the only step after the file is published. Catalog previews and library playback have separate browser audio elements, and only the library one is routed through Web Audio for the visualizer, because provider preview media has no CORS headers and would be silenced by it. Only one of the two plays at a time. The seek bar's waveform is one ffmpeg decode of the file on disk, one at a time, cached in SQLite (see [the player note](player.md#waveform-seek-bar)).
